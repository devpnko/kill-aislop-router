## 분석 수준과 아직 모르는 것

- **직접 관찰:** 선택된 정적 화면의 구성 요소, 위계, 면·경계·깊이·타이포·간격·색·이미지의 관계.
- **해석:** 왜 그 위계가 과제를 도울 수 있는지, 무엇을 평탄화하면 잃는지에 대한 연구 가설.
- **목표 제안:** 다른 제품에 맞춰 재설계할 compact/medium/wide 구성, 조작 상태, 콘텐츠 스트레스 검사.
- **미검증:** 실제 원 서비스 클릭·키보드·hover·모션·접근성·정보 정확도·같은 제품의 반응형 재배치.
- 이미지 뷰어의 1440×1000 크기를 원 앱의 viewport로 보지 않는다. 정확한 CSS, 폰트명, 색 토큰,
  간격 수치나 시트 구현 방식도 스크린샷에서 추정해 확정하지 않는다.
- 국내 친숙성은 요청에 따른 수집 기준이지 국민 인지도 조사나 기업 국적 판정이 아니다.
  현재 트래픽·인기 순위·사람이 직접 만들었다는 사실·디자인의 성공률을 증명하지 않는다.

원 서비스의 디자인을 모두 모범 답안으로 보지 않는다. 제목 말줄임, 작은 고지, 중첩 오류창,
혼동할 수 있는 색의 중복 의미도 함께 기록한다. 확인된 동작으로 표시한 것은 **0건**이다.
각 레시피는 기존 KSR component-recipe 형식의 **설계 초안**이며,
실제 프로젝트 기준·권리·독립 정식 검토·Owner 선택을 생략할 수 없다.

이 분석은 모든 제품을 흰색·얇은 선·무그림자로 만드는 규칙이 아니다.
사진이 중요한 탐색, 텍스트가 중요한 브리핑, 숫자가 중요한 작업대는 밀도와 에너지가 달라야 한다.
강조색 역시 “잘 알려진 브랜드의 색”이 아니라 **프로젝트의 현재 권한과 정보의 의미**에 맞춰 정한다.
다른 제품의 카드, 버튼, 탭을 각자 가져와 조합하는 것만으로 일관된 디자인이 되지는 않는다.

아래의 보존 중요도(primary 등)는 **목표 레시피의 의미적 중요도**다.
원 화면에서 크게 보인다는 뜻이 아니다. 실제 강조 정도는 관찰 문장에 따로 기록했다.
반응형 세 범위와 5개 조작 상태는 모두 적용 시 검증할 제안이며 원 서비스의 실행 증거가 아니다.

### 1. 카카오톡 — 원문을 남기는 대화 요약 카드

과제: 대화의 핵심을 빠르게 읽되 발화 원문·시점·처리 한계를 확인하고 요약을 복사한다.

근거: [통화 녹음 텍스트 이용 안내 모달](https://uibowl.io/name/%EC%B9%B4%EC%B9%B4%EC%98%A4%ED%86%A1?imgId=cmg0ha65f000mlb04d8mo58ga&detail=1) · [전사 원문 하단·고지·재생 컨트롤](https://uibowl.io/name/%EC%B9%B4%EC%B9%B4%EC%98%A4%ED%86%A1?imgId=cmg0ha67n000slb042cqwuvad&detail=1) · [AI 요약 카드·복사 완료 토스트](https://uibowl.io/name/%EC%B9%B4%EC%B9%B4%EC%98%A4%ED%86%A1?imgId=cmg0ha6a3000ylb04xk566so2&detail=1).
정적 3프레임 범위이며 실행 또는 반응형 증거가 아니다.

구성 요소:

- **context**: 상단 인물 식별과 통화 정보가 카드와 분리된다.
- **summary**: 흰 카드의 굵은 제목 아래 내어쓴 불릿이 다행 텍스트를 묶는다.
- **source**: 좌우 말풍선과 바깥의 작은 발화 재생 오프셋으로 화자와 녹음 내 위치를 나눈다. 기록의 날짜/절대 시각과는 구별된다.
- **caveat**: 사용 고지는 모달과 원문 하단의 별도 목록으로 표현된다.
- **copy-action**: 카드 하단 폭넓은 얇은 테두리 버튼과 아래쪽 어두운 토스트가 보인다.
- **playback**: 재생바·재생 버튼·시간은 화면 아래 독립된 영역에 모인다.

| 관찰 축 | 확인한 모습 |
| --- | --- |
| 면 | 원문 배경과 요약은 모두 밝지만 요약은 경계·그림자를 가진 별도 면, 재생 영역은 더 옅은 회색 면이다. |
| 경계·형태 | 안내창은 둥근 외곽과 확인 행의 가로선, 요약은 둥근 카드와 그보다 작은 곡률의 테두리 버튼을 쓴다. |
| 깊이 | 전체를 어둡게 하는 안내창과 낮은 그림자의 요약 카드, 국소 어두운 토스트가 서로 다른 층이다. |
| 타이포 | 요약 제목은 본문보다 굵고, 불릿 본문은 여러 줄이다. 기록 날짜·발화 재생 오프셋·고지는 더 옅은 회색과 낮은 시각적 강조로 분리된다. 폰트 파일·CSS 크기·정확한 명도/대비는 확인하지 않았다. |
| 간격·정렬 | 불릿의 둘째 줄은 텍스트 시작선에 맞고, 항목 사이는 한 항목 내부 행간보다 크다. 원문과 정책 사이에는 큰 단락 간격과 구분선이 있다. |
| 색의 역할 | 원문 발화는 회색/노란 면으로 대비되고, 요약의 작은 색 표식만 강조된다. 복사 버튼 자체는 강한 브랜드 면이 아니다. |
| 이미지 | 상단의 작은 인물 식별 이미지는 있으나 요약 내용을 장식하는 큰 이미지는 없다. |
| 모션 | 정지 이미지로 모션의 실행·시간·이징·감소 설정을 확인할 수 없다. **미관찰** |

위계와 전이 가설:

- 먼저 읽히는 것: 요약 문장과 원문이 중심이고 복사·재생은 각 경계 안에서 분리된다.
- 도우려는 판단: 요약만으로 충분한지, 어떤 원문을 더 확인해야 하는지 결정한다.
- 가능한 제약: 작은 폭에서 대화 맥락을 유지하면서 요약과 기록 관련 고지를 함께 제공해야 한다는 가설.
- 평탄화하면 잃는 것: 모든 내용을 동일 카드/글자 무게로 만들면 원문과 생성 요약, 처리 한계의 차이가 흐려진다.
- 대가: 두 표현을 남기면 신뢰 단서는 늘지만 스크롤 길이와 중복 읽기가 증가한다.
- 맞지 않는 상황: 채팅이 아닌 데이터 비교 화면에 좌우 말풍선까지 이식하면 정보 정렬을 방해한다.
- 필요한 데이터: 원문·시점·처리상태·접근권한·실제 오디오 유무를 제공하는 데이터가 필요하다.
- 복제 금지 경계: 개인 대화·화자 사진·브랜드 표식·노란 말풍선 조합을 복제하지 않는다. 법률상 동의 충족으로 해석하지 않는다.
- 적용 조건: 대상 기록과 원문이 실제 존재한다. / 요약·원문·처리 고지가 같은 권한/대상을 가리킨다.

정적 상태 근거:

- rest: 원문·요약이 채워진 정적 상태.
- success: 복사 완료를 뜻하는 토스트가 보인다. 이 세션에서 복사를 실행했다는 증거는 아니다.
- 미관찰: selected, hover, focus-visible, disabled, loading, empty, error.

다른 제품에서의 크기별 재구성 **제안**:

- compact: 한 열에서 대상→요약→제약→원문을 잇고 재생이 있으면 본문과 겹치지 않는 영역에 둔다. 접근: 문서 순서와 키보드 순서를 일치시키며 고지 상세·원문·복사에 직접 접근한다.
- medium: 요약과 원문을 함께 읽을 충분한 폭이 없으면 한 열을 유지하고 컨트롤만 정돈한다. 접근: 텍스트 확대 후에도 요약과 원문을 연결하는 접근을 유지한다.
- wide: 상하 또는 나란한 요약/원문을 과업에 따라 선택하되 대상·제약·복사/재생 접근은 모두 남긴다. 접근: 분할 배치에서도 키보드가 두 영역을 예측 가능한 순서로 이동한다.
- 중간 폭: 목표 제안: 분할의 두 열이 읽기 폭을 잃는 시점에 한 열로 돌아가고 요약을 축소 글자로 맞추지 않는다.

적용 후 확인할 검사 **제안 — 미실행**:

- 요약과 원문을 혼동하지 않는가? → 제목·영역·시점과 원문 접근이 구별되며 생성 실패가 원문으로 위장되지 않는다.
- 복사 피드백이 원문을 가리거나 스크롤을 옮기는가? → 실제 복사 결과와 일치하는 알림이 노출되고 본문·컨트롤 접근을 막지 않는다.
- 제약을 발견할 수 있는가? → 요약 가까이 핵심 고지와 상세 경로가 있으며 작은 글자 축소로 해결하지 않는다.
- 재생/키보드/확대 시 본문이 가려지는가? → 오디오가 있는 경우에만 컨트롤이 있고 모든 폭·확대에서 마지막 원문까지 접근 가능하다.

제한: 선택된 3개 정지 프레임만 분석했다. 원문 정확도·동의/개인정보 준수·요약 품질은 검증하지 않았다. 보이는 토스트와 재생바는 실제 상호작용 검증이 아니다. 소스의 정확한 폰트·CSS·반응형·hover·focus·모션은 미확인이다.

위계와 전이 가설:

- 먼저 읽히는 것: 제목→시간이 묶인 핵심 요약→상세 설명→관련 키워드/고지 순서의 읽기 차이가 보인다.
- 도우려는 판단: 해당 시점의 정보인지, 요약으로 충분한지, 더 읽거나 원문을 확인해야 하는지 결정한다.
- 가능한 제약: 한 화면 폭에서 빠른 훑기와 깊은 읽기, 생성 정보의 한계를 함께 전달해야 한다는 가설.
- 평탄화하면 잃는 것: 제목·시각·고지를 모두 같은 회색 크기로 줄이면 새로운 정보인지와 생성 요약의 한계가 묻힌다.
- 대가: 요약을 먼저 두면 빠르지만 본문 반복이 늘고 고지의 낮은 강조는 읽히지 않을 위험이 있다.
- 맞지 않는 상황: 행간이 넓은 읽기 형식을 고빈도 수치 비교 표 전체에 적용하면 비교 효율이 떨어진다.
- 필요한 데이터: 발행 시각, 갱신 여부, 날짜별 목록, 생성 한계와 원 출처의 상태가 필요하다.
- 복제 금지 경계: 원 기사 문구·녹색 브랜드·표식·금융 전망을 재사용하거나 정확성 증거로 삼지 않는다.
- 적용 조건: 발행/갱신 시각과 날짜 범위가 실제 데이터로 구별된다. / 핵심과 상세가 같은 항목에 속하며 출처 접근이 실제로 존재한다.

정적 상태 근거:

- rest: 목록·상세·상세 하단의 채워진 상태만 관찰했다. 하단 공백은 빈 결과 상태의 증거가 아니다.
- 미관찰: selected, hover, focus-visible, disabled, loading, empty, error, success.

다른 제품에서의 크기별 재구성 **제안**:

- compact: 한 열에서 날짜→항목 시각→제목→요약을 보존하고 긴 제목과 키워드는 자연스럽게 줄바꿈한다. 접근: 날짜 입력의 라벨과 오류를 키보드/보조기기로 접근하고 목록→상세→복귀 순서를 유지한다.
- medium: 읽기 폭을 유지한 한 열에 보조 탐색을 추가하되 본문을 과하게 넓히지 않는다. 접근: 본문 확대에서도 날짜·복귀 동작이 본문을 가리지 않는다.
- wide: 목록과 선택 상세를 분할할 수 있으나 날짜·제목·요약·제약은 동시에 접근 가능하고 읽기 열 너비를 제한한다. 접근: 분할 목록의 선택과 상세 제목을 연결하고 복귀 초점을 유지한다.
- 중간 폭: 목표 제안: 목록/상세 분할을 줄여도 요약·시각·원문/제약이 남아야 하며 글자 크기 축소로 폭을 맞추지 않는다.

적용 후 확인할 검사 **제안 — 미실행**:

- 날짜와 갱신 시점이 혼동되는가? → 각 항목의 시각과 선택 날짜가 분리되고 날짜 변경 후 내용·시각이 일치한다.
- 긴 제목에서 핵심이 사라지는가? → 제목·불릿·태그가 서로 겹치거나 중요한 문구를 잘라내지 않는다.
- 낮은 강조가 고지를 숨기는가? → 실제 배경 대비와 글자 확대에서 고지·원문 접근을 읽고 사용할 수 있다.
- 없는 자료와 로딩을 구별하는가? → 빈 날짜·오류·부분 요약·로딩 각각에 다른 메시지와 회복 경로가 있으며 빈 공백으로 끝나지 않는다.

제한: 현재 캡처는 모든 입력/오류 상태를 포함하지 않는다. 같은 제품의 여러 폭이나 실제 탭/날짜 이동을 검증하지 않았다. 시각·고지는 확인되지만 원문 출처의 완전성·금융 정보 정확도는 확인되지 않았다.

과제: 이미 등록된 수단을 확인하고 익숙한 제공자를 고른 뒤 입력 오류를 알아차린다.

위계와 전이 가설:

- 먼저 읽히는 것: 등록 대상 확인→제약 확인→이름/로고 선택→입력/오류가 단계별로 나뉜다.
- 도우려는 판단: 어느 제공자/수단을 추가할지와 왜 진행되지 않는지 판단한다.
- 가능한 제약: 옵션 수가 비교적 유한하고 사용자가 이름/로고를 알아볼 수 있다는 가설.
- 평탄화하면 잃는 것: 모든 셀을 똑같은 추상 아이콘으로 바꾸거나 오류를 약한 토스트로 줄이면 대상 인식과 진행 실패를 놓칠 수 있다.
- 대가: 격자는 빠르게 훑지만 옵션 증가와 긴 이름에 약하다. 중첩 모달은 집중을 주지만 초점/닫기 혼동과 입력 가림 위험이 있다.
- 맞지 않는 상황: 상세 조건을 열별로 비교해야 하는 대상까지 단순 로고 격자로 만들면 비교에 필요한 정보가 사라진다.
- 필요한 데이터: 현재 등록 목록·추가 가능 여부·제공자 목록·필드 검증 결과가 필요하다.
- 복제 금지 경계: 은행 로고·브랜드 버튼색·계정 예시를 이식하지 않는다. 금융 업무의 적법성/보안성은 이 화면으로 판단할 수 없다.
- 적용 조건: 동등한 선택 옵션이 실제로 존재하고 이름이 식별 단서다. / 제약과 등록/오류 상태를 사실대로 제공한다.

정적 상태 근거:

- rest: 등록 목록과 선택 격자의 정적 상태.
- error: 입력값을 다시 확인하라는 오류창이 보인다. 실제 오류를 발생시켜 본 것은 아니다.
- 미관찰: selected, hover, focus-visible, disabled, loading, empty, success.

다른 제품에서의 크기별 재구성 **제안**:

- compact: 폭이 좁으면 열 수를 줄이고 모든 이름·조건·입력·닫기를 남긴다. 키보드가 올라와도 오류와 주 행동에 접근한다. 접근: 전체 화면 또는 대화상자 중 하나의 의미 구조를 정하고 모든 선택·오류에 키보드로 접근한다.
- medium: 선택 셀의 읽기 폭이 충분한 열 수로 맞추며 입력 단계는 읽기/작성 폭을 제한한다. 접근: 시각 순서와 탐색 순서가 맞으며 필드 오류를 라벨과 연결한다.
- wide: 패널 안 셀 폭을 지나치게 늘리기보다 일정한 열 리듬과 제약·등록 목록을 유지한다. 접근: 닫기·취소·추가 후 포커스가 예측 가능하고 뒤 화면이 잘못 조작되지 않는다.
- 중간 폭: 목표 제안: 셀의 이름이 잘리기 전에 열 수를 바꾸고, 행/열 변화로 선택한 대상이나 초점이 바뀌지 않게 한다.

적용 후 확인할 검사 **제안 — 미실행**:

- 로고 없이도 선택 가능한가? → 이미지 누락·긴 이름에도 각 옵션과 현재 선택을 구별한다.
- 오류 후 입력을 고칠 수 있는가? → 입력값/선택 맥락이 유지되고 오류 설명과 문제 필드가 연결된다.
- 중첩 층의 클릭·키보드가 안전한가? → 한 활성 층만 조작되며 닫기/ESC 후 초점과 배경 스크롤이 정상 복구된다.
- 등록 제약을 뒤늦게 알게 되는가? → 선택·주 행동 전에 필요한 조건이 보이고 불가 시 사유가 유지된다.
- 삭제의 대상·결과와 복구 경로를 알 수 있는가? → 삭제 권한과 대상이 정확하고 결과·확인 또는 가능한 복구가 명시된다. 실패 때 목록 상태가 사라지지 않고 가린 식별 정보가 오류/로그/화면에 노출되지 않는다. 실제 테스트는 승인된 fixture에서 수행한다.

제한: 정지 화면에서 실제 등록/삭제/오류 회복을 실행하지 않았다. 격자 3열을 보았지만 그 열 수가 모든 화면 폭에 적합한 것은 아니다. 소스 중첩 모달의 접근성이나 안전성이 입증된 것이 아니다. 개인/계좌 예시는 기록하지 않으며 지급/보안 주장을 하지 않는다.

### 4. 네이버 여행 — 사진의 우선순위와 맥락을 분리한 여행 탐색

과제: 목적지를 아직 정하지 않은 사용자가 큰 사진으로 관심을 형성한 뒤, 제목·요약·주제 단서를 읽어 더 알아볼 대상을 고르는 구조를 연구한다. 가격이나 예약의 최신성은 분석 대상이 아니다.

근거: [여행 탐색·주제 카드](https://uibowl.io/website/%EB%84%A4%EC%9D%B4%EB%B2%84%20%EC%97%AC%ED%96%89?imgId=cmn71cbuz0007l104i9wyonsv) · [여행지 상세·사진·추천 보조열](https://uibowl.io/website/%EB%84%A4%EC%9D%B4%EB%B2%84%20%EC%97%AC%ED%96%89?imgId=cmn71cbym000fl104niwwsidp).
정적 2프레임 범위이며 실행 또는 반응형 증거가 아니다.

구성 요소:

- **focal-media**: 첫 캡처는 가운데 큰 가로 사진과 좌우 일부 사진을 나란히 보여 준다. 상세 캡처는 왼쪽 큰 사진 옆에 작은 사진들을 붙여 하나의 미디어 면을 만든다. 사진이 제목 영역보다 먼저 넓은 면적으로 등장한다.
- **decision-heading**: 사진 아래의 제목은 설명보다 크고 굵다. 탐색 화면은 중앙 사진 아래 좁아진 글 영역에서 제목이 두 줄로 이어지고, 상세 화면은 왼쪽 정렬된 짧은 이름 아래 보조 표기가 붙는다.
- **context-summary**: 제목 가까이에 작은 회색 설명을 두어 사진과 별도 읽기 영역을 만든다. 상세 화면에서는 이름 아래 보조 표기와 한 줄 설명의 순서가 보인다.
- **topic-selector**: 별도 하단 표면의 상단에 짧은 주제 칩이 모여 있다. 하나는 어두운 채움과 밝은 굵은 글자로, 나머지는 옅은 바탕과 어두운 글자로 구분된다.
- **navigation-cue**: 탐색 제목 아래에는 가는 회색 선과 짧은 파란 구간이 보인다. 상세 사진 모서리에는 카메라 아이콘·수량을 묶은 어두운 반투명 표시가 놓인다. 자동 전환이나 클릭 결과는 보이지 않는다.
- **context-actions**: 상세 요약 옆에는 작고 옅게 테두리 친 보조 조작이, 요약 아래에는 가로로 긴 행동 영역과 더 좁은 반응 수 영역이 있다. 사진보다 낮은 대비로 배치된다.
- **ancillary-discovery**: 주요 사진·설명 카드의 오른쪽 열에 최근 항목과 숙소 추천이 별도 흰 표면으로 쌓인다. 숙소 추천은 자체 사진과 강한 청록색 정보 블록을 포함하여 본문 밖에서도 눈에 띈다.

위계와 전이 가설:

- 먼저 읽히는 것: 큰 사진을 먼저 본 후 큰 제목과 짧은 설명을 읽게 하고, 주제 칩이나 상세 보조 행동은 그 다음 층에 둔다.
- 도우려는 판단: 불확실한 여행 관심을 이미지에서 시작하되, 제목과 설명으로 어떤 정보를 열어 볼지 구체화하는 결정을 도울 수 있다는 가설이다.
- 가능한 제약: 여행지의 분위기는 글만으로 전달하기 어렵고, 상세 탐색에는 사진·계획·추천처럼 성격이 다른 정보가 함께 필요할 가능성이 있다.
- 평탄화하면 잃는 것: 모든 요소를 동일한 텍스트 카드로 줄이면 사진의 선택 단서와 제목의 의미 보정이 약해진다. 반대로 사진만 크게 남기면 정보의 종류와 다음 행동이 불명확해진다.
- 대가: 큰 미디어는 관심 형성을 돕지만 한 화면의 비교 항목 수를 줄이고 네트워크·크롭 품질 의존도를 높인다.
- 맞지 않는 상황: 긴급한 운영 판단, 정확한 가격 정렬, 저속 연결에서 사진이 필수 정보를 지연시키는 경우에는 주 구조로 삼기 어렵다.
- 필요한 데이터: 사진 메타데이터와 설명의 연결은 확인 대상이며, 추천 가격·평점·수량·최근 이력은 별도 최신성·개인정보 처리 근거가 필요하다. 캡처의 수치는 사용하지 않는다.
- 복제 금지 경계: 사진·목적지 문구·상표·중앙 슬라이드의 고유 배치·상세 사진 모자이크를 복제하지 않는다. 전달 대상은 미디어와 의미 설명의 우선순위 관계뿐이다.
- 적용 조건: 합법적으로 확보한 실제 미디어가 대상의 차이를 설명할 때 적용한다. / 가격·가용성처럼 비교 정확성이 우선인 작업에는 별도 정형 비교 영역을 둔다. / 보조 추천이 주요 목적지 식별과 행동을 가리지 않는지 검증한다.

정적 상태 근거:

- rest: 탐색과 상세 화면의 정지 구성이 보인다. 두 화면 사이 전환을 실행한 증거는 아니다.
- selected: 주제 칩과 일부 탐색 항목에 채움 또는 밑줄 차이가 보인다. 현재 강조된 모습만 기록하며 선택 동작은 확인하지 않았다.
- 미관찰: hover, focus-visible, disabled, loading, empty, error, success.

다른 제품에서의 크기별 재구성 **제안**:

- compact: 주 미디어, 전체 제목, 설명, 주제 선택, 이동 단서, 관련 행동을 한 열에 둔다. 보조 제안은 요약 링크 뒤의 별도 영역으로 연다. 접근: 보조 제안 열기 조작으로 목록을 열고 닫은 뒤 원래 주 미디어 위치로 복귀한다.
- medium: 미디어와 설명을 한 열의 넓은 카드로 두고 주제 선택과 행동을 아래에 배치한다. 보조 제안은 본문 다음 행에서 노출한다. 접근: 모든 부분은 문서 순서에서 직접 접근한다.
- wide: 큰 주 열 안에 미디어·제목·요약·주제·이동·행동을 두고 더 좁은 보조열에 제안을 둔다. 접근: 주 열 다음에 보조열로 키보드와 읽기 순서가 이어진다.
- 중간 폭: 미디어를 계속 축소해 본문을 작게 만들지 않고, 주 제목의 읽기 폭과 보조열의 최소 내용 폭이 동시에 유지되지 않는 시점에 보조열을 아래로 옮긴다. 중간 폭에서 제목이 누락되거나 이동 조작이 사진 밖으로 이탈하지 않아야 한다.

적용 후 확인할 검사 **제안 — 미실행**:

- 사진이 변경되어도 전체 제목과 의미 설명이 같은 대상에 묶이는가? → 합성 데이터의 서로 다른 대상들을 이동할 때 이미지·제목·설명이 동일한 식별자를 유지하고 화면과 접근성 이름에서 교차 연결 오류가 없다.
- 서로 다른 피사체 위치와 긴 제목이 충돌하지 않는가? → 대표 크롭 스트레스 세트에서 주 피사체 및 모든 제목 줄이 보이고 이미지 없는 경우에도 다음 행동이 남는다.
- 보조 추천의 색과 사진이 주 대상 식별을 압도하지 않는가? → 세 폭의 실제 렌더에서 주 제목·주 이미지·주 행동이 보조 제안보다 먼저 읽히는지 별도 시각 검토하고 제품 의도와 일치한다.
- 포인터 없이 미디어와 주제를 탐색할 수 있는가? → 이동·열기·주제·닫기 순서가 문서 의미 순서와 일치하며 사진 경계가 포커스를 자르지 않는다.
- 가격과 최근 이력 등 실시간 정보가 이미지 탐색과 혼동되지 않는가? → 실시간 정보에 대상 제품의 기준 시각·출처·개인정보 정책을 별도 적용하고 샘플 캡처 값은 구현에 포함되지 않는다.

제한: 정적 2개 프레임의 상대 위계만 관찰했다. 스타일 수치·정확한 비율·폰트·CSS·동작은 추출하지 않았다. 이미지 권리 및 실제 데이터 최신성은 확인되지 않았으며 개인 계정·원문·가격을 전사하지 않는다. 예시는 아카이브 캡처이며 현행 서비스나 인간 제작 품질의 증거가 아니다. 세 폭 변형과 모든 상호작용 레시피는 적용 제안이며 테스트 실행·독립 승인·Owner 선택·ready pack이 아니다.

### 5. 네이버 여행 — 상위 지역과 하위 목적지를 병렬로 보여 주는 검색 패널

과제: 사용자가 목적지의 정확한 이름을 알면 검색하고, 모르면 상위 지역에서 국가·도시로 범위를 좁히는 보조 탐색 구조를 분석한다.

근거: [여행 탐색·주제 카드](https://uibowl.io/website/%EB%84%A4%EC%9D%B4%EB%B2%84%20%EC%97%AC%ED%96%89?imgId=cmn71cbuz0007l104i9wyonsv) · [지역·국가·도시 검색 패널](https://uibowl.io/website/%EB%84%A4%EC%9D%B4%EB%B2%84%20%EC%97%AC%ED%96%89?imgId=cmn71cbx0000bl104lpabjhm6).
정적 2프레임 범위이며 실행 또는 반응형 증거가 아니다.

구성 요소:

- **scope-tabs**: 패널 상단 두 범주가 같은 행에 있고, 오른쪽 항목은 더 진하고 굵은 글자와 밑줄로 강조된다.
- **query**: 상단 탭 아래 검색 입력이 패널 폭 대부분을 차지한다. 파란 외곽과 검색 아이콘, 상대적으로 옅은 안내 문자가 보인다. 키보드 포커스 여부는 확정하지 않는다.
- **parent-list**: 본문 왼쪽의 좁은 열에 큰 지역 범주가 연속 행으로 쌓인다. 비강조 행은 옅은 회색 바탕과 가는 분할선, 강조 범주는 흰 바탕과 파란 굵은 글자로 보인다.
- **child-list**: 오른쪽의 더 넓은 열에는 나라 단위 제목과 아래 목적지 행이 놓인다. 한 나라 구간은 펼쳐져 있고 뒤의 다른 나라 구간은 제목과 아래 방향 표시만 보인다.
- **item-type-cue**: 하위 행 앞에는 작은 국기 또는 둥근 사진이 있고 이름 뒤에는 낮은 대비의 유형 표기가 이어진다. 같은 열 안에서 나라와 도시를 문자와 이미지 형식으로 구분한다.
- **close-control**: 패널 오른쪽 위에 독립된 닫기 아이콘이 놓이며 범주 탭과 같은 상단 영역에 있다.

| 면 | 기본 여행 탐색 위에 흰 검색 패널이 오른쪽에 겹친다. 패널 밖의 사진과 제목은 여전히 보이며 전체 배경을 어둡게 덮는 모습은 없다. 패널 본문은 왼쪽 목록 바탕과 오른쪽 흰 결과 영역으로 갈린다. |
| 경계·형태 | 패널 외곽은 둥글고 검색 입력은 그보다 작은 곡률의 연속된 파란 경계를 가진다. 왼쪽 목록에는 수평 분할과 세로 경계가, 오른쪽 펼침 그룹에는 얇은 강조색 경계가 보인다. |
| 깊이 | 패널 바깥에 확산된 음영이 있어 기존 사진 카드보다 앞에 놓였음을 나타낸다. 하위 목적지 행마다 별도 부양 효과를 주지 않아 목록이 하나의 덩어리로 읽힌다. |
| 타이포 | 범위 탭은 일반 목록 글자보다 굵고, 선택 지역과 펼친 나라 제목은 강조색과 굵기를 함께 쓴다. 하위 이름과 유형 표기는 가까운 크기에서 대비가 다르다. 실제 글꼴과 가중치는 확인하지 않았다. |
| 간격·정렬 | 검색과 목록 사이에는 분할선이 있고, 상위 범주 행은 하위 도시 행보다 큰 세로 호흡을 갖는다. 하위 행의 이미지·이름·유형은 가깝게 정렬되어 하나의 선택 항목을 이룬다. 펼친 그룹과 다음 그룹 사이 간격이 더 크다. |
| 색의 역할 | 파랑은 검색 외곽, 선택된 지역, 펼친 그룹 제목·경계를 잇는다. 비선택 목록은 옅은 회색 면으로, 유형은 더 낮은 대비 회색으로 물러난다. 국기와 사진의 여러 색은 식별 보조이며 선택 상태와 동일한 색 체계는 아니다. |
| 이미지 | 나라 수준의 작은 직사각 국기와 도시 수준의 원형 사진이 보인다. 썸네일은 이름보다 작고 텍스트 없이 대상을 식별하기에는 부족하다. 이미지가 의미 유형을 보강하더라도 유형 문자가 별도로 남는다. |
| 모션 | 패널 열림·닫힘, 검색 제안 갱신, 그룹 펼침 애니메이션과 스크롤 경계는 실행하지 않았다. **미관찰** |

위계와 전이 가설:

- 먼저 읽히는 것: 상단의 직접 검색 경로와 본문의 두 단계 탐색 경로를 한 패널 안에 두고, 상위 지역과 현재 하위 목록을 동시에 보이게 한다.
- 도우려는 판단: 이름을 아는 사용자와 모르는 사용자가 동일한 맥락에서 서로 다른 진입 경로를 선택하게 도울 수 있다는 가설이다.
- 가능한 제약: 목적지 수가 많고 지리적 계층과 명칭 친숙도가 다르므로 단일 긴 목록만으로는 탐색 비용이 높을 가능성이 있다.
- 평탄화하면 잃는 것: 지역·나라·도시를 모두 같은 칩으로 나열하면 현재 탐색 범위와 유형이 사라진다. 반대로 검색만 남기면 정확한 철자를 모르는 사용자가 막힐 수 있다.
- 대가: 두 열은 계층을 동시에 보이게 하지만 좁은 폭에서 결과 이름과 유형의 공간을 압박한다. 썸네일은 친숙함을 주는 대신 데이터·로딩 비용이 추가된다.
- 맞지 않는 상황: 계층이 중첩·다중 소속되어 상위 하나로 분류하면 의미가 왜곡되는 자료나, 선택 가능한 대상이 몇 개뿐인 경우에는 과한 구조다.
- 필요한 데이터: 지역 분류, 이름 별칭, 검색 결과·가용 목적지·이미지 연결은 데이터 관리 대상이다. 현재 캡처는 검색 정확도나 최신 분류를 보장하지 않는다.
- 복제 금지 경계: 기존 서비스의 목적지 목록·국기 자산·사진·검색 문구·패널 좌표를 가져오지 않는다. 직접 검색과 계층 탐색의 병렬 관계만 대상 도메인 자료로 재설계한다.
- 적용 조건: 데이터가 실제로 상위·하위 관계를 가지며 동일 이름의 다른 유형을 구별해야 할 때 적용한다. / 현재 범주와 선택 결과를 텍스트로 보존한다. / 패널 밖 맥락 유지가 필요한 보조 탐색이며, 완료 시 돌아갈 명확한 출발점이 있어야 한다.

정적 상태 근거:

- rest: 기본 탐색과 검색 패널이 나타난 화면이 각각 있으나 열기 동작을 실행한 기록은 아니다.
- selected: 범위 탭, 상위 지역, 하위 펼침 그룹의 시각적 강조가 관찰된다.
- expanded: 한 하위 그룹은 여러 항목을 노출하고 다른 그룹은 제목만 보인다. 동시에 열 수 있는 개수는 알 수 없다.
- empty: 검색 입력에는 안내 문자가 보이고 입력한 검색어는 없다. 결과가 없는 검색 상태는 아니다.
- 미관찰: hover, focus-visible, disabled, loading, error, success.

다른 제품에서의 크기별 재구성 **제안**:

- compact: 범위 탭과 닫기를 상단, 검색을 다음 행에 둔다. 현재 상위 분류를 보이는 선택 행으로 유지하고 하위 목록을 아래에 펼치며 유형은 이름 아래 짧은 둘째 줄에 둔다. 접근: 상위 분류 행의 목록 열기·닫기로 범주를 바꿀 수 있고 현재 값은 항상 보인다. 하위 대상은 같은 문서 흐름에서 접근한다.
- medium: 상단 검색 아래에 좁은 분류 열과 넓은 하위 열을 둔다. 긴 유형은 이름 아래로 줄바꿈하되 분류 값은 결과 헤더에도 남긴다. 접근: 두 열은 분류 다음 결과 순서로 탐색하며 닫기는 상단에서 접근한다.
- wide: 상단의 범위·검색·닫기와 두 열의 분류·결과를 고정된 의미 순서로 배치한다. 각 목록은 공간이 부족하면 이름이 줄바꿈되는 제한된 세로 스크롤 영역을 가진다. 접근: 상위 행 선택 후 결과 영역의 설명을 제공하고 포커스는 사용자가 이동할 때만 결과로 간다.
- 중간 폭: 두 열의 이름과 유형이 최소 읽기 폭을 지키지 못하면 상위 분류를 현재 값이 보이는 선택 행으로 바꾸고 하위 결과를 아래로 옮긴다. 패널 자체의 가로 스크롤로 문제를 숨기거나 글자를 축소하지 않는다.

적용 후 확인할 검사 **제안 — 미실행**:

- 상위 분류를 바꾸어도 사용자는 현재 결과의 소속을 알 수 있는가? → 모든 폭에서 현재 범주가 텍스트로 남고 결과 헤더·선택 상태가 동일한 범주를 가리킨다.
- 같은 이름의 다른 유형을 잘못 선택하지 않도록 구별하는가? → 동일명·상이한 유형의 테스트 자료에서 각 행의 이름·유형·소속이 읽기 순서에 포함되고 서로 다른 접근성 이름을 가진다.
- 직접 검색과 분류 이동의 상태 변경 규칙이 명확한가? → 검색 중 범위를 바꿀 때 입력·결과·선택의 유지 또는 초기화가 계약대로 작동하며 빈 결과에서 수정 경로가 남는다.
- 패널을 닫으면 원래 맥락으로 복귀하는가? → 키보드로 열기·분류·하위 탐색·닫기를 완료하고 닫힌 뒤 원래 트리거가 포커스를 회복한다.
- 긴 이름과 많은 결과가 제한된 영역에서 잘리지 않는가? → 세 폭 및 경계 사이 폭에서 전체 이름과 유형을 읽을 수 있고 스크롤 중 포커스 행과 닫기 접근 경로가 사라지지 않는다.

제한: 검색 패널은 완전 디코딩된 대체 캡처만 사용했고, 최초 불완전 캡처는 근거에서 제외했다. 채택 캡처는 출처 인덱스의 해당 프레임 digest로 고정한다. 정적 검색 패널 한 장은 실제 검색 정확도·스크롤 동작·복수 그룹 열기·포커스 복귀를 증명하지 못한다. 입력의 강조 테두리는 보이지만 hover 또는 focus-visible로 명명할 입력 방식 증거가 없다. 컴팩트·중간·넓은 변형은 모두 target-proposal이며 해당 원본의 반응형 동작을 추정하지 않는다.

익명화된 전체 8축 레시피·조작 5상태·스트레스 사례는 JSON의 `naver-travel-hierarchical-search` 항목에 있다.

### 6. 네이버 지도 웹 — 검색·분류·본문·피드백을 연결한 도움말 공개

과제: 지도 자체의 조작이 아니라 고객센터에서 문제에 맞는 도움말을 찾고, 플랫폼별 설명을 읽고, 유용성 피드백까지 도달하는 정보 공개 구조를 분석한다.

정적 3프레임 범위이며 실행 또는 반응형 증거가 아니다.

구성 요소:

- **help-query**: 큰 서비스 도움말 제목 아래에 길고 둥근 흰 검색 면이 색 있는 헤더와 흰 본문의 경계를 걸친다. 검색 아이콘은 입력의 오른쪽 끝에 놓인다.
- **topic-filter**: 본문 위 짧은 주제 칩들이 두 줄로 이어진다. 하나는 초록 채움과 밝은 글자로, 다른 항목은 옅은 면과 낮은 대비 글자로 보인다.
- **disclosure-trigger**: 접힌 목록은 각 행에 질문 제목과 오른쪽 아래 방향 표시를 둔다. 본문이 보이는 캡처에서는 제목이 더 굵고 위 방향 표시가 있다. 얇은 수평선이 행 또는 기사 머리를 구분한다.
- **context-tabs**: 열린 설명 상단에 두 운영체제 표기가 가로로 있고 하나는 초록·굵은 문자와 작은 점으로, 다른 것은 회색으로 표시된다.
- **article-body**: 질문 제목보다 안쪽으로 들어간 본문 영역에 문단, 굵은 단계 제목, 번호나 불릿, 주의 설명이 이어진다. 다른 기사 캡처에서는 강조 단어만 초록으로 두고 여러 문단을 일정한 줄 간격으로 쌓는다.
- **instruction-figure**: 본문 아래에 기기 설정 화면을 붙인 설명 그림이 보인다. 그림 속 일부 영역에 붉은 사각 강조가 있으나 하단은 캡처 경계에 닿아 전체 이미지가 보이지 않는다.
- **usefulness-feedback**: 본문 다음의 넓은 여백 아래 가는 테두리의 가로 피드백 면이 있다. 짧은 질문과 표정 아이콘을 포함한 두 둥근 응답 조작을 한 행에 묶는다.

| 관찰 축 | 확인한 모습 |
| --- | --- |
| 면 | 검색 진입 화면은 채도 있는 넓은 헤더와 흰 콘텐츠 면의 대비가 크다. 열린 도움말은 흰 본문 면을 길게 사용하고 각 문단을 카드로 다시 감싸지 않는다. 마지막 피드백만 별도 얇은 외곽을 가진다. |
| 경계·형태 | 검색은 캡슐처럼 둥글고 분류 칩도 둥글다. 질문 목록과 본문 구조는 가는 수평선으로 정리되어 모서리 있는 반복 카드보다 읽기 흐름이 연속적이다. 피드백 면의 곡률은 응답 버튼보다 작다. |
| 깊이 | 검색 입력 아래에는 가벼운 음영이 있지만 기사 본문은 눈에 띄는 부양 효과 없이 흰 바탕에 놓인다. 오른쪽의 둥근 보조 조작은 음영으로 분리되며, 본문 구조와 다른 층이다. |
| 타이포 | 진입의 서비스 제목은 질문 목록보다 훨씬 크고 밝다. 열린 질문과 단계 제목은 본문보다 굵고, 문단·번호 안내는 상대적으로 일정한 글자 크기로 유지된다. 선택된 플랫폼은 무게와 색으로, 비선택 플랫폼은 낮은 대비로 구분된다. |
| 간격·정렬 | 분류 칩끼리의 간격은 작지만 분류와 첫 질문 사이에는 별도 여백이 있다. 접힌 질문들은 일정한 행 높이 리듬을 갖고, 열린 본문은 제목보다 들여쓰기되어 단계 사이를 문장 사이보다 넓게 띄운다. 피드백 전 여백은 본문 문단 간격보다 크다. |
| 색의 역할 | 진입 헤더는 초록에서 청록으로 이어지는 큰 색 면이고, 도움말 내부에서는 초록이 주제 선택·플랫폼 선택·부분 강조에만 국소적으로 보인다. 문서는 주로 어두운 문자와 흰 바탕이다. 설명 그림 속 붉은 표시의 역할은 제품 오류색이 아니라 그림의 주목 지점이다. |
| 이미지 | 정보 전달용 기기 화면 그림과 단계 설명의 결합이 보인다. 다른 기사의 하단은 그림 없이 문자와 피드백으로 구성되어 모든 도움말에 이미지를 강제하는 구조로 볼 수 없다. 지도 캔버스·경로 편집·장소 검색 결과는 관찰되지 않았다. |
| 모션 | 질문 펼침·접힘, 플랫폼 전환, 검색 결과 갱신, 피드백 응답, 상단 이동의 실행 및 애니메이션은 관찰하지 않았다. **미관찰** |

위계와 전이 가설:

- 먼저 읽히는 것: 문제 제목을 빠르게 훑는 목록에서 해당 본문을 펼쳐 읽고, 필요하면 플랫폼 구분을 해석한 뒤 피드백을 남기게 하는 순서가 시각적으로 분리된다.
- 도우려는 판단: 내 문제와 맞는 제목인지, 내 환경에 맞는 설명인지, 설명이 충분했는지를 차례로 판단하도록 도울 수 있다는 가설이다.
- 가능한 제약: 도움말의 길이와 플랫폼 차이는 크지만 목록 단계에서는 여러 문제 제목을 빠르게 비교해야 할 가능성이 있다.
- 평탄화하면 잃는 것: 모든 질문을 큰 카드로 만들면 제목 탐색 밀도가 낮아지고, 본문을 동일한 카드 조각으로 쪼개면 단계의 연속성과 주의사항 맥락이 끊길 수 있다.
- 대가: 많은 내용을 한 페이지에서 공개하면 맥락은 유지되지만 긴 문서의 탐색 위치와 접기 복귀를 관리해야 한다. 플랫폼 탭은 분량을 줄이는 대신 잘못된 조건 선택 위험이 생긴다.
- 맞지 않는 상황: 경고를 먼저 읽어야 하는 안전 절차나 여러 문서를 동시에 대조해야 하는 작업에서는 기본 접힘이 핵심 내용을 숨길 수 있다.
- 필요한 데이터: 제품 버전·기기 설정 경로·지원 범위가 바뀌면 도움말이 낡을 수 있으므로 검토일과 해당 버전을 별도 관리해야 한다. 캡처는 현재 절차 정확성을 입증하지 않는다.
- 복제 금지 경계: 고객센터 문구·브랜드 헤더·기기 화면·특정 색 전환을 복사하지 않는다. 목록 제목과 연속 본문, 조건 분기, 사후 피드백의 역할 관계만 이전한다.
- 적용 조건: 사용자가 해결하려는 구체적인 문제 단위로 문서가 나뉘어 있을 때 적용한다. / 플랫폼 조건이 실제 설명 차이를 만들 때만 조건 선택을 둔다. / 피드백은 답변 내용을 다 읽지 않아도 강제로 요구하지 않고, 응답 후 처리 내용을 별도 설계한다.

정적 상태 근거:

- rest: 여러 도움말 제목이 접힌 목록 상태로 보인다.
- selected: 한 주제 칩과 한 플랫폼 항목의 강조 모습이 보인다. 선택 이벤트는 기록되지 않았다.
- expanded: 서로 다른 도움말의 본문 공개 모습과 위 방향 표시가 보인다. 같은 기사의 연속 스크롤이나 탭 전환 결과라고 단정하지 않는다.
- empty: 검색 입력에는 안내 문자가 보이며 검색어가 없는 모습이다. 검색 결과 없음이나 내용 없는 기사의 증거는 아니다.
- 미관찰: hover, focus-visible, disabled, loading, error, success.

다른 제품에서의 크기별 재구성 **제안**:

- compact: 검색·주제·질문·조건·본문·그림·피드백을 한 열로 두고 긴 질문과 칩은 줄바꿈한다. 피드백 응답은 질문 아래에 놓는다. 접근: 문서 순서로 모든 부분에 접근하고 큰 그림은 이름 있는 확대 조작으로 별도 보기한다.
- medium: 검색과 필터를 본문 위에 두고 문서 폭을 제한한다. 조건은 기사 첫머리에, 그림은 관련 단계 아래, 피드백은 문서 끝에 유지한다. 접근: 공개된 기사 끝의 접기 또는 질문으로 복귀 경로와 피드백 응답을 모두 제공한다.
- wide: 넓은 진입 영역 안에서도 질문 목록과 기사 본문은 읽기 폭을 제한한다. 가로 피드백 배열은 질문과 두 응답이 충분히 들어갈 때만 사용한다. 접근: 검색에서 주제, 질문, 조건, 단계, 그림, 피드백 순으로 직접 접근한다.
- 중간 폭: 검색과 칩은 먼저 줄바꿈하고 본문 글자를 줄이지 않는다. 피드백 행이나 그림이 읽기 폭을 넘기기 전에 세로 배열로 바꾸며 전체 페이지의 가로 스크롤을 만들지 않는다.

적용 후 확인할 검사 **제안 — 미실행**:

- 이 패턴의 범위가 지도 조작이 아니라 도움말 탐색으로 명확한가? → 컴포넌트 명세·문구·테스트가 질문 검색·본문 공개·조건·피드백으로 한정되고 지도 성능이나 경로 정확성 주장이 없다.
- 긴 본문을 읽고 접어도 질문을 잃지 않는가? → 긴 기사에서 키보드로 접기 후 해당 질문을 다시 볼 수 있고 포커스가 문서 시작이나 배경으로 이동하지 않는다.
- 현재 환경 선택과 실제 설명이 일치하는가? → 서로 다른 조건의 테스트 문서에서 선택 이름·본문 버전·접근성 상태가 같은 조건을 가리킨다.
- 설명 그림이 없어도 핵심 지시를 이해할 수 있는가? → 그림을 실패시킨 경우 관련 단계와 대체 설명이 남고 확대를 닫으면 원래 단계로 돌아온다.
- 유용성 응답과 문제 해결 성공을 구별하는가? → 긍정·부정·실패·재시도 테스트에서 기록 결과만 알리고 실제 문제 해결을 확인 없이 선언하지 않는다.

제한: 이 자료는 지도 고객센터 화면이며 지도 UI·지도 성능·경로 탐색의 근거로 사용할 수 없다. 열린 두 캡처는 서로 다른 기사다. 같은 기사의 진행 과정 또는 조건 전환 전후라고 간주하지 않는다. 설명 그림 일부는 화면 아래에서 잘리며 전체 그림이나 모든 안내 문구가 보인다고 주장할 수 없다. 기사 정확도, 접근성 적합, 브라우저 실행, 현재 버전, 사용자 해결률을 검증하지 않았다.

익명화된 전체 8축 레시피·조작 5상태·스트레스 사례는 JSON의 `naver-map-web-help-disclosure` 항목에 있다.

### 7. 토스 비즈니스 — 작성 필드와 전송 결과 모형을 나란히 둔 알림 편집

과제: 알림의 제목·본문·이동 위치를 작성하면서 오른쪽의 수신 화면 모형에서 예상 정보 계층을 대조하고 검토 단계로 넘기는 구조를 분석한다.

근거: [푸시 작성 폼·미리보기·검토 요청](https://uibowl.io/website/%ED%86%A0%EC%8A%A4%20%EB%B9%84%EC%A6%88%EB%8B%88%EC%8A%A4?imgId=cmmjxg6qf000nky04kgkkbjx1) · [문구 제안 로딩 팝오버](https://uibowl.io/website/%ED%86%A0%EC%8A%A4%20%EB%B9%84%EC%A6%88%EB%8B%88%EC%8A%A4?imgId=cmmjxg6r7000pky04vci947qw) · [문구 제안 근거·적용 버튼](https://uibowl.io/website/%ED%86%A0%EC%8A%A4%20%EB%B9%84%EC%A6%88%EB%8B%88%EC%8A%A4?imgId=cmmjxg6ss000tky04qixj9vdp).
정적 3프레임 범위이며 실행 또는 반응형 증거가 아니다.

구성 요소:

- **delivery-mode**: 상단의 별도 흰 섹션에 가로 선택 띠가 있고 오른쪽 항목은 흰 면·진한 글자, 왼쪽은 더 옅은 문자로 보인다. 설명 한 줄이 그 아래에 붙는다.
- **content-tabs**: 편집 섹션 제목 아래에 두 가지 콘텐츠 경로가 있고 한 항목은 진한 문자와 짧은 밑줄로 강조된다.
- **title-field**: 왼쪽 편집 열의 첫 입력은 한 줄 흰 면이고, 위의 작은 라벨·필수 표지, 옆의 작은 변수 조작, 입력 오른쪽 문자 수 표시가 붙는다.
- **body-field**: 제목 아래 더 높은 다중 줄 입력이 있고, 라벨·필수 표지·변수 조작이 같은 패턴을 반복한다. 세 번째 캡처에서는 이 입력 외곽이 파랗게 강조된다.
- **destination-field**: 본문 다음에 목적지 주소 입력이 좁은 한 줄로 놓인다. 설명 아이콘과 고정된 앞부분처럼 보이는 진한 문자, 더 옅은 뒤쪽 안내가 함께 있다. 주소 값은 전사하지 않는다.
- **preview**: 오른쪽에 밝은 기기 모형이 있고 그 안에 작은 알림 면이 놓인다. 위에는 작은 두 항목 전환이 있다. 편집 필드가 있는 옅은 배경 안에서 모형은 더 밝은 면으로 분리된다.
- **template-reference**: 편집·미리보기 묶음 아래에 가로 전체 폭의 식별 코드 입력과 작은 도움말이 있고 그 다음 넓은 시험 발송 조작이 낮은 대비로 표시된다.
- **workflow-actions**: 최하단의 별도 흰 가로 면에 검토 필요성을 알리는 굵은 안내가 왼쪽, 보조 저장과 파란 검토 요청 조작이 오른쪽에 묶인다.

| 모션 | 입력 타이핑, 미리보기 갱신 지연, 탭 전환, 저장·시험 발송·검토 요청의 실행은 관찰하지 않았다. **미관찰** |

위계와 전이 가설:

- 먼저 읽히는 것: 입력란과 수신 모형을 같은 편집 영역에 둔 뒤, 발송을 위한 식별 정보와 검토 행동을 아래에 별도 층으로 둔다.
- 도우려는 판단: 문구가 수신자에게 어떤 크기·순서로 보일지 대조하고 발송 전 검토가 필요한지를 판단하는 데 도움을 줄 수 있다는 가설이다.
- 가능한 제약: 작성자는 제목·본문·연결 위치·발송 방식·검토 절차를 함께 관리해야 하고 편집 화면의 넓은 문구가 실제 수신 영역에는 다르게 보일 가능성이 있다.
- 평탄화하면 잃는 것: 미리보기를 장식 카드로 줄이거나 필드와 멀리 분리하면 입력 결과의 대응이 약해진다. 저장·시험 발송·검토 요청을 동급 단추로 묶으면 업무 단계의 차이를 읽기 어려워진다.
- 대가: 병렬 미리보기는 결과 대조에 유리하지만 입력 폭을 줄인다. 시각적으로 정교한 모형은 실제 모든 기기에서 같은 결과가 나온다는 오해를 만들 수 있다.
- 맞지 않는 상황: 법적 문구·여러 언어·동적 변수처럼 실제 결과가 크게 달라지는데 한 모형만 확정적 결과처럼 보여 주는 경우에는 위험하다.
- 필요한 데이터: 변수 치환, 권한, 발송 방식, 글자 제한, 검토 상태, 실제 기기 출력은 별도 데이터와 실행 검증이 필요하다. 캡처 간 문구 대응만으로 실시간 동기화를 입증할 수 없다.
- 복제 금지 경계: 소스의 기기 모형·앱 아이콘·주소 체계·문구·캠페인 정보를 복사하지 않는다. 필드와 결과의 병렬 대조 및 검토 행동의 분리를 대상 제품 고유 규칙으로 설계한다.
- 적용 조건: 실제 수신 형식을 신뢰할 수 있는 모형으로 표현할 수 있을 때 적용한다. / 미리보기와 서버 처리·실제 전달의 차이를 설명한다. / 저장·시험·검토·실제 발송의 권한과 결과를 구별한다.

정적 상태 근거:

- rest: 필드가 비어 있고 수신 모형에 기본 안내가 있는 편집 모습이다.
- selected: 발송 방식과 콘텐츠 경로 및 미리보기 상단 전환에 강조된 항목이 보인다. 실제 탭 전환 결과는 없다.
- populated: 입력 문구와 모형의 대응되는 위치에 내용이 보이는 캡처가 있다. 입력 이벤트나 자동 갱신 시간을 확인한 것은 아니다.
- empty: 주요 입력이 빈 상태이고 안내 문자가 보인다. 저장 가능한 빈 문서인지 여부는 알 수 없다.
- 미관찰: hover, focus-visible, disabled, loading, error, success.

다른 제품에서의 크기별 재구성 **제안**:

- compact: 전달 방식, 현재 변형, 제목, 본문, 목적지 다음에 미리보기를 즉시 보이는 한 열로 두고 식별 정보와 업무 행동을 뒤에 둔다. 미리보기는 기본 접힘으로 숨기지 않는다. 접근: 모든 부분은 문서 순서로 접근하며 입력 후 미리보기로 이동할 이름 있는 링크를 추가할 수 있다.
- medium: 입력과 미리보기를 위아래의 연결된 편집 영역으로 유지한다. 폭이 확보되는 구간에서는 짧은 필드만 같은 행에 두며 검토 면은 하단에 전체 폭으로 둔다. 접근: 키보드는 입력 묶음 다음 미리보기 요약, 식별 정보, 검토 행동 순서로 이동한다.
- wide: 더 넓은 편집 열과 옆의 수신 모형을 병렬로 두고 전달 방식·변형은 위에, 식별 정보·검토 행동은 아래 전체 폭으로 둔다. 접근: 각 필드에서 연결된 미리보기 부분의 이름을 확인할 수 있으며 어느 열에도 독립적인 함정 스크롤을 만들지 않는다.
- 중간 폭: 입력 최소 읽기 폭과 모형 내 문자열 폭을 동시에 유지할 수 없으면 두 열을 세로로 재배치한다. 전체 모형이나 본문을 축소해 해결하지 않고, 각 필드의 수량·변수 조작·오류 설명이 충돌하는 경계 폭을 따로 검사한다.

적용 후 확인할 검사 **제안 — 미실행**:

- 입력과 미리보기가 같은 문서 버전을 보여 주는가? → 짧은 입력·빠른 연속 수정·변수 갱신 테스트에서 모든 수신 문자열이 마지막 입력 버전과 일치하거나 미반영 상태가 명시된다.
- 변수의 실제 길이가 제한과 출력에 반영되는가? → 최대 길이·누락·다국어 값을 치환한 후 제한 안내와 미리보기 줄바꿈이 대상 제품 계약과 일치한다.
- 저장·시험·검토·실제 발송이 구별되는가? → 각 행동의 권한·전제·확인·결과 메시지가 다르며 검토 요청만으로 발송 완료를 선언하지 않는다.
- 작은 폭에서 제목·본문·미리보기가 숨겨지지 않는가? → 세 폭과 중간 폭에서 세 주 부분 및 검토 행동이 보존되고 라벨·수량·변수 조작은 서로 겹치지 않는다.
- 모형의 한계를 사용자가 인지할 수 있는가? → 미리보기 주변에 지원 범위와 실제 출력 차이 안내가 있으며 여러 수신 환경의 별도 검증 없이는 완전 동일 출력을 주장하지 않는다.

제한: 상단 일부가 잘린 캡처이므로 전체 페이지 제목·단계·모든 라벨의 가시성을 입증하지 않는다. 세 캡처의 필드와 모형 대응은 정적 관찰이다. 실시간 미리보기, 입력 검증, 저장·발송의 실행은 확인하지 않았다. 색이 옅은 조작의 disabled 의미와 파란 외곽의 focus-visible 의미를 확정하지 않는다. 기기 모형 정확성·접근성 적합·품질·인간 작성 여부를 판정하지 않는다.

익명화된 전체 8축 레시피·조작 5상태·스트레스 사례는 JSON의 `toss-business-composer-preview` 항목에 있다.

### 8. 토스 비즈니스 — 편집 필드 옆에 붙는 문구 제안·근거·적용

과제: 전체 작성 업무를 바꾸지 않고 현재 필드 주변에서 문구 후보와 수정 이유를 검토하는 보조 도구의 시각 구조를 분석한다. 생성 기술의 종류나 실행 정확도는 검증 대상 근거가 없다.

근거: [푸시 작성 폼·미리보기·검토 요청](https://uibowl.io/website/%ED%86%A0%EC%8A%A4%20%EB%B9%84%EC%A6%88%EB%8B%88%EC%8A%A4?imgId=cmmjxg6qf000nky04kgkkbjx1) · [문구 제안 로딩 팝오버](https://uibowl.io/website/%ED%86%A0%EC%8A%A4%20%EB%B9%84%EC%A6%88%EB%8B%88%EC%8A%A4?imgId=cmmjxg6r7000pky04vci947qw) · [문구 제안 근거·적용 버튼](https://uibowl.io/website/%ED%86%A0%EC%8A%A4%20%EB%B9%84%EC%A6%88%EB%8B%88%EC%8A%A4?imgId=cmmjxg6ss000tky04qixj9vdp).
정적 3프레임 범위이며 실행 또는 반응형 증거가 아니다.

구성 요소:

- **context-field**: 제목 또는 본문 입력이 주 작성 열에 남아 있고 두 보조창 캡처에서는 각각 다른 필드 외곽이 파랗게 강조된다. 오른쪽 수신 모형도 가려지지 않은 상태로 함께 보인다.
- **suggestion-surface**: 필드 왼쪽에 작은 흰 떠 있는 면이 놓인다. 위의 작은 회색 기능 이름 아래, 세 번째 캡처에서는 제안 문구가 더 진하고 굵게 보인다. 두 캡처의 패널 높이와 위치는 같지 않다.
- **rationale**: 제안 행 아래에 옅은 바탕의 둥근 인셋이 있고 짧은 진한 항목명과 여러 줄의 낮은 대비 설명이 쌓인다. 제안 자체와 이유가 서로 다른 표면으로 분리된다.
- **apply-control**: 제안 문구 오른쪽에 작은 옅은 파란 면과 진한 파란 글자를 가진 적용 조작이 있다. 주변의 최종 검토 요청 버튼보다 작고 가볍다.
- **progress-cue**: 내용이 없는 큰 흰 보조창 가운데 부근에 서로 다른 크기의 파란 점이 보인다. 진행 대기처럼 읽히는 정적 표지이나 움직임이나 네트워크 호출의 증거는 아니다.

| 관찰 축 | 확인한 모습 |
| --- | --- |
| 면 | 문구 도구는 기존 인셋 편집 면을 대체하지 않고 옆에 흰 패널로 추가된다. 제안이 있는 캡처에서는 패널 내부의 이유만 다시 옅은 면으로 묶어, 제안 결과와 설명을 같은 표면 계층으로 평준화하지 않는다. |
| 경계·형태 | 바깥 제안 패널은 둥근 모서리이고 이유 인셋은 더 작은 곡률을 가진다. 현재 입력은 선명한 파란 전체 외곽을, 적용 조작은 작은 채움 면을 가져 필드·보조 설명·행동의 종류를 구별한다. |
| 깊이 | 제안 패널 둘레에 확산된 음영이 있어 작성 영역 위에 떠 있음을 나타낸다. 이유 인셋은 그림자보다 면 차이로만 구별되어 패널 안에서 또 다른 팝업처럼 읽히지 않는다. |
| 타이포 | 도구 이름은 작고 옅고, 제안 문구는 그보다 진하고 굵다. 이유 인셋은 짧은 표제와 더 가볍고 여러 줄인 설명으로 나뉜다. 적용 문자는 작은 크기를 유지해 최종 업무 행동보다 낮은 위계다. |
| 간격·정렬 | 보조창은 현재 입력의 왼쪽에 가까이 붙지만 입력 텍스트와 미리보기는 노출된 채로 남는다. 후보가 보이는 캡처의 첫 행은 문구와 적용을 가깝게 묶고 그 아래 이유 블록과 작은 간격으로 분리된다. 점만 보이는 캡처는 내부 여백이 훨씬 크다. |
| 색의 역할 | 파랑이 현재 입력 외곽·진행처럼 보이는 점·적용 조작을 연결한다. 이유 설명은 낮은 대비 회색 계열이며 경고나 오류색으로 표현되지 않는다. 이 색 연결만으로 동일 비동기 작업 또는 실제 AI 호출을 증명할 수 없다. |
| 이미지 | 제안 패널에는 사진·인물·대화 아바타가 없다. 내용과 이유를 문자로 설명하고 진행 표지는 단순한 점으로 한정한다. 하단·우측의 다른 도구 아이콘은 이 제안의 근거가 아니다. |
| 모션 | 점이 회전·점멸하는지, 패널이 필드를 따라 이동하는지, 후보가 교체되는지, 적용 시 텍스트가 바뀌는지는 실행하지 않았다. **미관찰** |

위계와 전이 가설:

- 먼저 읽히는 것: 현재 입력을 그대로 노출하면서 옆에 작은 후보·이유·적용을 놓아, 제안을 원문 및 수신 모형과 비교하게 한다.
- 도우려는 판단: 제안이 어떤 개선을 의도하는지 이해한 뒤 현재 필드에 반영할지 스스로 선택하는 결정을 도울 수 있다는 가설이다.
- 가능한 제약: 사용자는 문구 수정을 위해 전체 업무 화면을 벗어나기 어렵고 자동 수정이 뜻을 바꾸거나 책임 소재를 흐릴 위험이 있을 가능성이 있다.
- 평탄화하면 잃는 것: 이유를 숨기고 즉시 덮어쓰기만 하면 제안의 의미 변경을 검토할 수 없다. 반대로 전면 대화창으로 확대하면 현재 입력과 미리보기의 비교 맥락을 잃을 수 있다.
- 대가: 국소 패널은 문맥을 보존하지만 화면 가장자리와 좁은 폭에서 잘릴 수 있다. 짧은 이유는 판단 비용을 줄이는 대신 언어·도메인 예외를 생략할 수 있다.
- 맞지 않는 상황: 법적 약속, 가격, 의학적 표현처럼 작은 단어 변경이 책임을 바꾸는 문장에 검토 절차 없이 적용하거나, 필드 변경 뒤 오래된 후보를 그대로 적용하면 위험하다.
- 필요한 데이터: 생성 요청의 입력 범위·버전·상태·보존 정책·실패 원인은 별도 계약이 필요하다. 캡처의 점이나 후보 문장만으로 AI 모델·API·정확성·개인정보 처리를 알 수 없다.
- 복제 금지 경계: 소스의 제안 문구·언어 규칙 설명·작성 내용·패널 좌표를 재사용하지 않는다. 현재 필드, 후보, 설명, 명시적 반영의 관계만 익명화한 적용안으로 넘긴다.
- 적용 조건: 수정 대상 필드와 제안의 적용 범위가 명확한 작업에 사용한다. / 원문을 보존하고 반영을 사용자가 명시적으로 선택하게 한다. / 근거 설명이 검증된 사실인지 단순한 모델 제안인지 표시하고 과도한 권위를 부여하지 않는다.

정적 상태 근거:

- rest: 동일 작성 영역에 별도 제안 패널이 보이지 않는 캡처가 있다. 패널을 닫은 동작이나 기본 설정을 보여 주지는 않는다.
- selected: 서로 다른 입력의 강조 외곽과 옆 패널의 위치가 보인다. 현재 적용 대상처럼 읽히는 정적 관계만 기록한다.
- proposal-visible: 후보와 이유 및 적용 조작이 동시에 보인다. 제안 생성 완료나 정확성 검증을 실행한 증거는 아니다.
- loading: 본문 대신 점이 보이는 대기형 패널 모습만 관찰된다. 실제 진행 여부·지속 시간·애니메이션·백엔드 상태는 알 수 없다.
- 미관찰: hover, focus-visible, disabled, empty, error, success.

다른 제품에서의 크기별 재구성 **제안**:

- compact: 현재 입력 다음에 후보·상태·이유·반영을 인라인으로 배치한다. 원본과 후보를 번갈아 숨기는 전면 전환을 사용하지 않는다. 접근: 현재 필드 이후 문서 순서에서 후보와 이유를 읽고 반영 또는 도움 닫기를 실행할 수 있다.
- medium: 가장자리 여유가 충분하면 현재 입력 옆에 후보를 붙이고 부족하면 바로 아래로 옮긴다. 진행 상태는 후보 영역 안에서 일정한 위치를 가진다. 접근: 원본과 후보 사이에 명시적 관계 이름을 제공하고 닫으면 원래 입력으로 복귀한다.
- wide: 필드와 결과 모형을 가리지 않는 옆 공간에 후보 면을 둔다. 긴 이유는 패널 높이를 늘리되 페이지 경계에 닿으면 인라인으로 전환한다. 접근: 키보드로 원본·후보·이유·반영을 순서대로 접근하며 도구에서 빠져나올 수 있다.
- 중간 폭: 후보가 화면 밖으로 나가거나 원본 또는 미리보기를 덮기 전에 원본 아래 인라인 면으로 전환한다. 글자를 작게 하거나 이유를 제거하지 않고 긴 내용은 문서 높이에 자연스럽게 포함한다.

적용 후 확인할 검사 **제안 — 미실행**:

- 늦게 도착한 후보가 다른 필드나 새 원문에 적용되지 않는가? → 입력 변경·필드 전환·응답 역전 테스트에서 후보가 대상 식별자와 입력 버전에 묶이고 낡은 반영은 차단된다.
- 후보를 보았다는 이유로 원문이 바뀌지 않는가? → 열기·읽기·닫기만으로 원문이 변하지 않고 명시적 반영 뒤에는 해당 변경만 되돌릴 수 있다.
- 원문·후보·수신 모형의 비교 맥락이 남는가? → 세 폭과 중간 폭에서 원문과 후보가 읽히고 패널이 미리보기나 검토 행동을 가리지 않는다.
- 짧은 이유가 검증된 사실처럼 과장되지 않는가? → 내용 검토에서 근거 출처와 불확실성을 구분하고 민감한 의미 변경에는 별도 승인 또는 검토가 요구된다.
- 대기·후보 없음·오류가 구별되는가? → 각 상태를 문자와 접근성 상태로 식별할 수 있고 움직이는 점만으로 진행을 설명하지 않는다.

제한: 정적 제안 UI는 AI 모델 사용·생성 정확도·실제 호출·개인정보 처리·응답 시간을 증명하지 못한다. 대기형 점의 움직임과 적용 후 결과는 없으며, 프레임 순서를 실제 입력 이력으로 재구성하지 않는다. 필드 강조를 키보드 포커스, 후보 표시를 적용 성공으로 간주하지 않는다. 소스 원문과 제안 문장을 전사하지 않았고 본 레시피는 익명화한 적용 제안이지 승인된 생성 기능 명세가 아니다.

익명화된 전체 8축 레시피·조작 5상태·스트레스 사례는 JSON의 `toss-business-local-assistance` 항목에 있다.

### 9. 카카오페이 — 비교 행과 맥락을 남기는 상세 시트

과제: 관심 목록의 수치를 빠르게 비교하고 목록 맥락을 남긴 채 별도 시트의 이슈 그룹을 읽는다.

근거: [증권 관심 목록·그룹 요약](https://uibowl.io/name/%EC%B9%B4%EC%B9%B4%EC%98%A4%ED%8E%98%EC%9D%B4?imgId=cmgnsyutl0003ld043cfu0jkd&detail=1) · [그룹 이슈 바텀시트](https://uibowl.io/name/%EC%B9%B4%EC%B9%B4%EC%98%A4%ED%8E%98%EC%9D%B4?detail=1&imgId=cmgnsyuv40007ld04gm46idz5).
정적 2프레임 범위이며 실행 또는 반응형 증거가 아니다.

구성 요소:

- **scope**: 큰 상위 탭과 밑줄 있는 하위 탭이 구별된다.
- **summary**: 흰 요약 면 안 붉은/파란 막대와 설명이 있다. 막대의 정확한 분모는 이 캡처로 알 수 없다.
- **item-identity**: 아이콘 옆 굵은 이름, 아래 회색 식별자, 작은 국가 표지가 묶인다.
- **metrics**: 행 오른쪽에 색과 화살표가 있는 변화율, 그 아래 가격이 정렬된다.
- **detail-scope**: 옅게 가려진 배경 위 시트, 상단 닫기와 두 개의 동일 폭 탭이 있다.
- **issue-groups**: 그룹 제목·개수·짧은 설명, 세로 연결선, 한 항목 아래 옅은 펼친 설명 면이 보인다.

| 관찰 축 | 확인한 모습 |
| --- | --- |
| 면 | 목록 자체는 행의 반복이고 요약과 상세 설명에만 별도 밝은 면이 쓰인다. 상세 시트는 배경과 별도 층이다. |
| 경계·형태 | 목록 행을 각각 둥근 카드로 감싸지 않는다. 요약·확장 설명은 둥근 직사각형, 시트 위 모서리는 더 큰 곡률이다. |
| 깊이 | 어두운 배경 덮개와 밝은 시트 경계가 앞뒤를 만든다. 실제 그림자 CSS·중첩 순서는 미확인이다. |
| 타이포 | 이름·그룹 제목은 굵고 식별자·설명은 작고 옅다. 가격과 변화율은 우측 읽기 열을 이룬다. |
| 간격·정렬 | 아이콘과 이름의 좁은 간격, 항목 행의 반복 간격, 요약→목록의 큰 간격을 분리한다. 시트 그룹 사이 간격도 행 사이보다 크다. |
| 색의 역할 | 붉은/파란 수치가 회색과 진한 텍스트 사이에서 부각된다. 선택 탭은 검정 밑줄이며 수치 강조와 다른 문법이다. |
| 이미지 | 작은 식별 아이콘이 행을 찾는 보조 역할을 한다. 목록 전체를 채우는 장식 이미지는 없다. |
| 모션 | 정지 이미지로 모션의 실행·시간·이징·감소 설정을 확인할 수 없다. **미관찰** |

위계와 전이 가설:

- 먼저 읽히는 것: 이름과 수치의 두 열을 먼저 훑고 관련 이슈는 별도 층으로 읽는다.
- 도우려는 판단: 어떤 항목의 값이 얼마나 변했는지 비교하고 이슈 그룹의 설명을 더 읽을지 결정한다. 시트를 특정 단일 종목 상세로 단정하지 않는다.
- 가능한 제약: 좁은 화면에서 많은 수치의 비교와 긴 설명을 동시에 노출하기 어렵다는 가설.
- 평탄화하면 잃는 것: 각 행을 큰 카드로 바꾸거나 숫자의 오른쪽 정렬을 없애면 연속 비교가 느려지고 시트 제목과 근거도 혼동된다.
- 대가: 시트는 맥락을 남기지만 긴 내용과 확대 글자에서는 스크롤·초점 관리 부담이 커진다.
- 맞지 않는 상황: 서로 다른 의미의 수치를 같은 상승/하락 색에 강제로 맞추거나 긴 원문 읽기를 좁은 시트에 가두면 해롭다.
- 필요한 데이터: 지표 단위·시점·방향 의미·그룹 분류·관련 근거가 필요하다.
- 복제 금지 경계: 금융 색상 의미, 회사 아이콘, 실제 종목·거래 데이터를 일반 제품에 그대로 이식하지 않는다.
- 적용 조건: 항목별 지표의 단위·기준시각이 비교 가능하다. / 관련 설명의 범위가 전체 목록/그룹/개별 항목 중 무엇인지 명확하고 복귀할 목록 맥락이 있다.

정적 상태 근거:

- rest: 관심 목록과 그룹 상세의 정적 상태.
- selected: 하위 탭의 밑줄과 펼친 설명 면이 보인다. 실제 선택 조작은 실행하지 않았다.
- 미관찰: hover, focus-visible, disabled, loading, empty, error, success.

다른 제품에서의 크기별 재구성 **제안**:

- compact: 한 열 비교 행을 유지하며 이름은 줄바꿈하되 값과 겹치지 않는다. 상세는 충분한 높이와 닫기 경로를 갖는다. 접근: 상세 내 초점 범위와 닫기·복귀를 실제로 검증한다.
- medium: 넓어진 목록에서도 숫자 열을 유지하고 상세 폭을 읽기에 맞춘다. 접근: 확대 글자에서 닫기·탭·그룹 설명이 가려지지 않게 한다.
- wide: 목록과 이슈 시트를 나란히 놓을 수 있으나 현재 목록 범위와 이슈 그룹의 연결을 실제 데이터로 설명한다. 접근: 목록에서 이슈 시트로 이동하는 순서와 범위를 보조기기로 전달한다.
- 중간 폭: 목표 제안: 병치된 시트를 접는 순간에도 목록 범위·단위·시각·복귀 위치를 보존하며 값이 이름 위를 덮지 않게 한다.

적용 후 확인할 검사 **제안 — 미실행**:

- 비교 값이 실제로 비교 가능한가? → 동일 열의 단위와 시점이 명시되고 긴 값도 다른 행·이름과 겹치지 않는다.
- 상세에서 목록으로 돌아올 수 있는가? → 실제 클릭·키보드·닫기 후 시트를 연 조작의 초점과 목록 읽기 위치가 복귀한다.
- 색상만 알아야 방향을 아는가? → 부호·문구를 통해 무채색에서도 의미가 유지된다.
- 집계 막대가 근거 없는 권위를 만드는가? → 분모·기간·미수신 항목 처리 규칙을 확인할 수 있다.

제한: 정적 선택 모습만 확인했다. 실제 시트/탭/그룹 조작과 초점은 미실행이다. 집계 막대의 정확한 의미와 지표의 정확성은 확인되지 않았다. 동일 제품의 다른 폭과 시트 내부 스크롤 규칙은 미확인이다. 이슈 그룹 시트를 특정 한 종목의 상세로 확정하지 않는다.

익명화된 전체 8축 레시피·조작 5상태·스트레스 사례는 JSON의 `kakaopay-watchlist-sheet` 항목에 있다.

### 10. 카카오페이 — 시각·뉴스·연관 항목을 나눈 시간 목록

과제: 발행 시각 순으로 관련 뉴스를 훑고 어떤 항목과 연결되는지 파악한다.

근거: [관련 뉴스 타임라인](https://uibowl.io/name/%EC%B9%B4%EC%B9%B4%EC%98%A4%ED%8E%98%EC%9D%B4?detail=1&imgId=cmgnsyuxr000fld04nc3njick).
정적 1프레임 범위이며 실행 또는 반응형 증거가 아니다.

구성 요소:

- **scope**: 뉴스 탭이 진한 밑줄로 선택되어 있다.
- **timestamp**: 작은 시각이 제목 왼쪽의 독립된 열에 있다. 희미한 세로 선이 행을 연결한다.
- **headline**: 굵은 제목은 여러 줄이고 일부는 말줄임표가 보인다.
- **thumbnail**: 있는 항목만 우측 둥근 작은 사진이 있고 없는 항목도 존재한다.
- **association**: 제목 밑 외곽선 캡슐 안 이름·색 있는 변화값이 붙는다.
- **dismiss**: 시트 오른쪽 위에 작은 닫기 동작이 보인다.

| 관찰 축 | 확인한 모습 |
| --- | --- |
| 면 | 흰 시트 하나 안에 연속된 뉴스 행이 있으며 뉴스마다 두꺼운 별도 카드는 없다. |
| 경계·형태 | 희미한 시간 안내선과 얇은 칩 외곽, 둥근 썸네일이 다른 단위를 구별한다. |
| 깊이 | 배경 덮개와 시트는 층이지만 뉴스 행끼리는 깊이를 주지 않는다. CSS 구현은 알 수 없다. |
| 타이포 | 굵은 여러 줄 제목이 가장 강하고 작은 시각과 항목 칩은 보조다. 일부 긴 제목은 줄여져 있다. |
| 간격·정렬 | 시간 열→제목 열→선택적 썸네일 열이 나뉘고 칩은 제목 아래에 붙는다. 행 사이 간격은 제목 내부보다 크다. |
| 색의 역할 | 진한 제목·회색 시각·옅은 안내선에 연관 항목의 붉은/파란 수치만 국소 강조된다. |
| 이미지 | 사진이 없는 뉴스도 보이며 텍스트 비중이 커진다. 사진 없는 행에 임의 장식이 채워져 있지 않다. |
| 모션 | 정지 이미지로 모션의 실행·시간·이징·감소 설정을 확인할 수 없다. **미관찰** |

위계와 전이 가설:

- 먼저 읽히는 것: 언제→무슨 사건→어떤 항목 관련인지 세 줄기의 정보를 구별한다.
- 도우려는 판단: 새로운 사건인지, 제목을 더 읽을 가치가 있는지 판단한다.
- 가능한 제약: 좁은 시트 안에 시각·긴 제목·불규칙한 이미지 유무·연관 지표를 함께 넣어야 한다는 가설.
- 평탄화하면 잃는 것: 모든 행을 같은 높이 사진 카드로 고정하면 제목과 시각이 잘리고 사건보다 이미지가 우선될 수 있다.
- 대가: 간결한 행은 훑기 좋지만 제목 말줄임과 약한 시각/출처 강조가 정보 손실을 만들 수 있다.
- 맞지 않는 상황: 시간 순서보다 조건별 정밀 비교가 중요한 화면을 이 시간 목록 하나로 대체하면 비교가 어려워진다.
- 필요한 데이터: 발행/수정 시각·중복 사건·원문 주소·권리 있는 이미지·연관 항목이 필요하다.
- 복제 금지 경계: 기사 문구·사진·종목 이름을 복제하지 않고 시간/내용/연관 관계만 전이한다.
- 적용 조건: 시간순 읽기가 주요 과제다. / 제목·발행 시각·원문 접근과 관련 항목이 실제로 제공된다.

정적 상태 근거:

- rest: 시각별 뉴스가 채워진 상태만 관찰했다.
- selected: 뉴스 탭의 선택 표시가 보이나 탭 전환 성공을 검증하지 않았다.
- 미관찰: hover, focus-visible, disabled, loading, empty, error, success.

다른 제품에서의 크기별 재구성 **제안**:

- compact: 좁은 폭에서는 시각을 제목 위로 옮길 수 있으나 제목·원문·연관 항목이 남는다. 접근: 긴 제목을 펼치거나 원문에서 읽는 경로를 제공하고 작은 칩만 유일한 링크로 만들지 않는다.
- medium: 시간 열과 본문 열을 유지하고 이미지 슬롯은 실제 제목 공간을 보고 배치한다. 접근: 탭→뉴스→원문→복귀의 초점 순서를 검증한다.
- wide: 목록과 상세 병치를 선택하더라도 뉴스의 읽기 폭과 시간 열의 정렬을 유지한다. 접근: 상세와 목록의 현재 항목 관계와 초점 복귀를 유지한다.
- 중간 폭: 목표 제안: 시각 열과 이미지 열이 제목을 압박하는 구간에서 먼저 재배치하고 제목 크기 축소나 무조건 말줄임으로 해결하지 않는다.

적용 후 확인할 검사 **제안 — 미실행**:

- 핵심 제목이 줄임으로 없어지는가? → 비슷한 제목을 구별하는 마지막 구절도 전체 보기에서 접근 가능하고 겹침이 없다.
- 사진 없거나 실패하면 행이 망가지는가? → 제목·시각·원문이 남고 잘못된 대체 사진이나 큰 빈 칸을 강제하지 않는다.
- 뉴스의 시각·출처를 실제로 알 수 있는가? → 게시자·발행/수정 시각·원문 연결을 검증하고 미확인을 표시한다.
- 새 자료가 읽던 위치를 빼앗는가? → 추가 자료를 알려도 현재 항목과 초점이 임의로 이동하지 않는다.

제한: 이 캡처의 각 행에서 게시자/원 출처의 완전한 표시는 확인되지 않았다. 말줄임 제목은 관찰했으나 전체 보기 경로는 실행하지 않았다. 썸네일 실패·빈 목록·실제 새 뉴스 삽입·반응형 동작은 미확인이다.

### 11. 네이버 파파고 웹 — 원문·결과 두 영역과 필기 후보 보조 입력

과제: 원문과 번역 결과를 나란히 대조하면서 키보드 외 입력 방식의 필기 결과를 후보 목록으로 검토하는 구성과 그 상태 차이를 분석한다.

근거: [필기 인식 보조창 빈 상태](https://uibowl.io/website/%EB%84%A4%EC%9D%B4%EB%B2%84%20%ED%8C%8C%ED%8C%8C%EA%B3%A0?imgId=cm7u1cwvr000gjr0c3vr61xj7) · [필기·인식 후보 표시](https://uibowl.io/website/%EB%84%A4%EC%9D%B4%EB%B2%84%20%ED%8C%8C%ED%8C%8C%EA%B3%A0?imgId=cm7u1cwwe000kjr0cb6pwx3vs) · [후보 반영된 원문·번역문](https://uibowl.io/website/%EB%84%A4%EC%9D%B4%EB%B2%84%20%ED%8C%8C%ED%8C%8C%EA%B3%A0?imgId=cm7u1cwwp000mjr0czwqnpgv5).

구성 요소:

- **language-context**: 두 큰 패널의 상단에 각각 언어 표기가 있고 원문 쪽에는 교환형 아이콘이 보인다. 원문·결과의 언어 조건이 각 패널 안에서 구분된다.
- **source-pane**: 왼쪽 패널에는 큰 원문 글자와 오른쪽 위 지우기 표시, 아래쪽 문자 수가 있다. 세 번째 캡처에서는 패널 외곽이 초록으로 강조되고 원문이 더 길게 보인다.
- **target-pane**: 오른쪽 패널은 원문과 나란한 큰 결과 글자를 가진다. 그 아래 더 작은 회색 보조 표기가 있으며, 아래쪽에는 결과 수정·평가처럼 읽히는 작은 조작들이 보인다.
- **handwriting-canvas**: 원문 패널 아래쪽에 큰 흰 필기 보조창이 떠 있다. 첫째·셋째 캡처는 빈 입력 안내와 넓은 공백, 둘째는 굵기가 일정하지 않은 손글씨 선이 넓게 차지한다.
- **candidate-strip**: 보조창 위의 얇은 띠는 빈 상태에서 중앙 안내를, 필기가 있는 캡처에서는 여러 텍스트 후보를 가로로 보여 준다. 첫 후보만 초록이고 뒤의 후보는 어두운 문자다.
- **pane-tools**: 두 패널 하단에 아이콘 도구들이 가는 세로선으로 분할되어 있다. 원문 오른쪽 끝의 번역 행동은 큰 초록 채움이고 필기 아이콘도 초록으로 보인다. 결과 쪽은 음성·복사·저장·공유 형태의 선 아이콘들이다.
- **canvas-tools**: 필기창 아래 띠에 되돌리기와 삭제 형태의 작은 아이콘이 왼쪽, 닫기 문자 조작이 오른쪽에 놓인다. 빈 캡처에서는 앞의 두 아이콘이 더 옅고 필기 캡처에서는 더 진하게 보인다.

위계와 전이 가설:

- 먼저 읽히는 것: 입력과 결과를 같은 크기 계층에서 대조하게 하고, 필기 입력은 원문에 가까운 별도 작업창 안에서 후보 확인과 정리를 수행하도록 보인다.
- 도우려는 판단: 직접 그린 문자열을 곧바로 믿기보다 후보를 살펴 원문에 반영할 대상을 선택하고 결과와 비교하도록 도울 수 있다는 가설이다.
- 가능한 제약: 키보드 입력이 어렵거나 문자를 정확히 모르는 경우에도 원문을 작성해야 하고, 필기 인식은 여러 후보를 가질 가능성이 있다.
- 평탄화하면 잃는 것: 필기 도구를 단순한 작은 아이콘만 남기거나 후보 확인 없이 자동 삽입하면 인식 오류를 검토할 기회를 잃는다. 결과만 보여 주면 원문 오류와 번역 오류를 구분하기 어렵다.
- 대가: 큰 필기 영역은 입력에 유리하지만 본문 아래 공간을 점유하고 페이지 조작과 제스처 충돌을 만들 수 있다. 병렬 패널은 비교를 돕지만 좁은 화면에서는 읽기 순서를 다시 설계해야 한다.
- 맞지 않는 상황: 결과의 정확성 검토 없이 중요한 계약·의료·법률 의사결정을 내리거나, 손동작을 수행할 수 없는 사용자에게 필기만 강요하는 경우에는 부적절하다.
- 필요한 데이터: 필기 인식·언어 감지·번역의 모델 상태와 서버 응답·데이터 보관은 별도 계약이 필요하다. 캡처 간 문자열·길이 차이는 실제 응답 성공이나 정확성의 검증이 아니다.
- 복제 금지 경계: 원문·결과·필기 문자열·브랜드 아이콘·광고·폰트·정확한 패널 치수를 옮기지 않는다. 두 문서의 비교와 보조 입력 후보 검토 관계만 익명화한다.
- 적용 조건: 대체 입력 방식이 실제 사용자 작업에 필요하고 후보를 검토할 수 있는 경우 적용한다. / 원문과 결과의 언어 조건 및 갱신 상태를 명확히 한다. / 필기 전용 장치가 없어도 키보드 또는 다른 입력으로 동일한 핵심 작업을 수행할 수 있어야 한다.

정적 상태 근거:

- rest: 원문·결과가 이미 존재하고 필기창은 빈 상태인 구성이 보인다. 초기 진입의 전체 빈 번역 화면은 아니다.
- selected: 한 필기 후보와 필기 도구가 강조되어 있고 이후 캡처의 원문 외곽이 강조된다. 후보 선택 동작·입력 방식은 검증하지 않았다.
- handwriting-present: 보조창에 필기 획과 여러 후보가 동시에 보인다. 획 생성이나 인식 시간을 측정한 것은 아니다.
- populated-change: 이전 캡처보다 원문·결과 텍스트가 길어지고 필기창이 다시 비어 있다. 그 사이의 삽입·번역 동작을 실제로 관찰한 것은 아니다.
- empty: 필기 영역이 비어 있고 안내가 보인다. 원문·번역 패널까지 빈 상태라는 의미는 아니다.
- 미관찰: hover, focus-visible, disabled, loading, error, success.

다른 제품에서의 크기별 재구성 **제안**:

- compact: 언어 조건과 원문, 후보·필기·필기 도구, 결과와 문서 도구를 세로로 배치한다. 원문과 결과 모두 직접 보이는 문서 영역으로 유지한다. 접근: 원문에서 필기와 후보, 결과로 이동하는 이름 있는 경로를 제공하고 페이지 스크롤과 필기 제스처를 구별한다.
- medium: 원문과 결과를 세로 문서로 두되 각 도구는 문서에 붙인다. 필기창은 원문 다음의 넓은 인라인 영역으로 두어 결과를 가리지 않는다. 접근: 후보는 키보드와 포인터로 접근하고 닫으면 원문 입력 위치로 돌아간다.
- wide: 원문과 결과를 병렬로 두고 필기창을 원문 아래 또는 빈 보조 공간에 연결한다. 후보와 필기 도구는 창 내부에 유지한다. 접근: 원문·필기 후보·결과가 읽기 순서에서 연결되고 어느 창도 결과의 핵심 내용을 덮지 않는다.
- 중간 폭: 두 문서의 읽기 폭이 부족해지면 병렬을 세로로 바꾸고 필기창을 인라인으로 옮긴다. 후보는 읽기 가능한 줄바꿈 또는 이름 있는 제한 스크롤을 사용하되 주 원문·결과를 탭 뒤에 숨기지 않는다.

적용 후 확인할 검사 **제안 — 미실행**:

- 후보 반영이 올바른 원문 위치와 공백에 적용되는가? → 문장 중간·선택 영역·문장 끝·언어 혼합 테스트에서 삽입 위치·앞뒤 내용·문자 수가 계약과 일치하고 되돌릴 수 있다.
- 표시된 결과가 현재 원문에 대응하는지 알 수 있는가? → 원문 변경·늦은 응답·언어 전환에서 결과 버전이 일치하거나 미갱신 표지가 명시된다.
- 필기와 페이지 스크롤이 충돌하지 않는가? → 지원 입력 장치별로 필기 면 안의 획과 바깥 스크롤이 의도대로 분리되고 키보드 대체 입력으로도 완료할 수 있다.
- 모든 후보를 키보드로 읽고 선택할 수 있는가? → 후보 순서·포커스·확정 상태가 명확하고 선택 후 원문으로 돌아오며 비선택 후보를 놓치지 않는다.
- 긴 원문과 긴 결과의 비교가 모든 폭에서 가능한가? → 세 폭과 중간 폭에서 원문·결과·언어가 모두 보존되고 글자를 줄이거나 핵심 문장을 자르지 않는다.

제한: 세 장은 필기 빈 면·획과 후보·길어진 원문과 결과의 정적 차이일 뿐 실제 연속 실행을 입증하지 않는다. 번역 정확도·필기 인식 성능·입력 지연·보조창 이동·접근성 적합을 검증하지 않았다. 원문 밑 점선의 발생 주체와 도구의 비활성 의미를 단정하지 않는다. 민감할 수 있는 원문·결과·필기 내용·계정 정보·광고 문구는 전사하지 않았으며 대상 레시피에 포함하지 않는다.

구성 요소:

- **method-list**: 좁은 흰 세로 면 안에 계좌와 카드 범주가 굵은 제목·수량처럼 보이는 작은 숫자·펼침 표시로 구분된다. 첫 캡처 카드 범주에는 추가 행만, 마지막 캡처에는 일부 보이는 어두운 카드 타일과 추가 타일이 함께 있다.
- **add-method**: 카드가 없는 모습에서는 가로로 긴 얇은 테두리 행에 원형 더하기와 진한 이름이 보인다. 카드가 표시되는 모습에서는 옆의 점선 타일이 추가 조작을 담당하는 구조로 보인다.
- **registration-heading**: 등록 화면 맨 위에 닫기 아이콘과 굵은 제목 일부, 그 아래 테두리 버튼이 보인다. 제목 상단이 잘려 있어 전체 제목·단계·첫 화면 위치는 확인할 수 없다.
- **credential-fields**: 카드 번호는 여러 작은 입력 블록, 다음 정보는 나란한 두 필드, 마지막 비밀 정보는 전체 폭 필드로 배열된다. 라벨은 굵고 작은 붉은 필수 표지가 있으며 일부 값은 점으로 가려져 있다. 마지막 필드는 더 진한 외곽을 가진다.
- **field-guidance**: 분절 번호 아래에는 작은 낮은 대비 안내가 두 줄로 놓이고, 번호 행 위쪽에는 작은 어두운 카드 종류 배지가 있다. 안내가 무엇을 제한하는지 원문은 전사하지 않는다.
- **numeric-keypad**: 입력 면 바로 아래에 강한 보라색 숫자 키패드가 붙는다. 숫자가 비순차적으로 배치되어 있고 아래에 전체 삭제·한 글자 삭제 형태 조작이 보인다. 숫자 순서·입력값은 기록하지 않는다.
- **return-control**: 목록은 왼쪽 위 뒤로 가기 형태 아이콘, 입력은 위쪽 닫기 아이콘을 가진다. 좁은 흰 면 오른쪽에는 스크롤 막대가 보인다. 닫기·뒤로 가기의 실제 결과는 알 수 없다.

위계와 전이 가설:

- 먼저 읽히는 것: 목록에서 기존 수단과 추가 경로를 구분한 뒤, 등록 화면에서는 라벨·분절된 입력·큰 숫자 키패드를 순서대로 인식하게 한다.
- 도우려는 판단: 기존 수단을 사용할지 새 수단을 추가할지 구별하고, 입력 중 어떤 필드에 무엇을 넣는지 파악하도록 도울 수 있다는 가설이다.
- 가능한 제약: 민감한 짧은 숫자 입력이 여러 종류이며 화면을 많이 차지하는 키패드와 오류 안내·복귀 경로를 함께 수용해야 할 가능성이 있다.
- 평탄화하면 잃는 것: 기존 수단과 추가 경로를 같은 정보 타일로 만들면 실행 경로가 흐려진다. 모든 숫자를 하나의 무라벨 입력으로 합치거나 라벨을 안내 문자로만 대체하면 입력 종류와 가림 상태를 판단하기 어렵다.
- 대가: 전용 키패드는 현재 입력 맥락을 크게 보여 주지만 가용 화면 높이를 줄이고 일반 키보드·보조 기술과의 호환 위험을 만든다. 분절 필드는 형식을 보조하지만 붙여넣기와 수정에 불편할 수 있다.
- 맞지 않는 상황: 검증되지 않은 자체 보안 키패드로 결제 제공자의 보안 기능을 대체하거나, 가려진 값과 카드 타일 표시를 인증·결제 완료의 증거로 쓰는 경우에는 위험하다.
- 필요한 데이터: 기관 지원 여부·인증·등록 결과·카드 표시 데이터는 권한 있는 결제 시스템 응답에 종속된다. 화면의 카드 타일은 현재 유효성·실제 등록 성공·잔액 정확성의 증거가 아니다.
- 복제 금지 경계: 카드·계좌·잔액·기관 로고·홍보 문구·키패드 숫자 순서를 전사하거나 복제하지 않는다. 목록·추가·라벨 있는 민감 입력·복귀의 역할 분리만 이전한다.
- 적용 조건: 결제수단 추가가 실제 승인된 업무이고 검토된 결제·보안 제공자의 규칙을 따르는 경우에만 사용한다. / 민감값을 로그·분석·스크린샷에 남기지 않는 별도 구현 계약이 필요하다. / 키패드가 있더라도 읽기·오류 수정·닫기 경로와 다른 입력 지원 범위를 확인한다.

정적 상태 근거:

- rest: 결제수단을 관리하는 목록 모습이 두 장 있다. 실제 로그인·계좌 권한·현재 데이터와는 무관한 아카이브 정지 화면이다.
- input-emphasis: 마지막 입력의 외곽이 더 진하고 키패드가 보인다. 현재 입력 대상처럼 보이는 외형만 기록한다.
- empty: 카드 범주에는 등록 카드 타일 없이 추가 조작이 보인다. 다른 결제수단 범주까지 빈 상태라는 뜻은 아니다.
- registered-looking: 카드 범주에 카드 타일 일부와 수량 표시가 보인다. 이 변화가 앞 입력의 실제 제출 결과인지 검증되지 않았다.
- 미관찰: selected, hover, focus-visible, disabled, loading, error, success.

다른 제품에서의 크기별 재구성 **제안**:

- compact: 목표 제안: 목록/추가와 등록은 별도 단계로 구분한다. 등록 단계는 제목·필드·안내·입력 도구·명확한 복귀를 한 열로 유지하고 기존 수단 목록/추가는 이전 관리 단계에서 접근한다. 접근: 현재 단계에서 모든 필드·안내·취소에 접근한다. 명시적인 취소/돌아가기로 관리 단계의 목록과 추가 출발점에 돌아간다. 미저장 입력 처리와 초점 복귀는 실제로 검증한다.
- medium: 목표 제안: 읽기 폭을 제한한 등록 단계 안에서 관련 짧은 필드만 같은 행에 둔다. 목록/추가는 관리 단계로 분리하고 현재 입력·안내·복귀를 숨기지 않는다. 접근: 등록 필드·안내·입력 도구·취소를 순서대로 접근하고, 취소/복귀 후 관리 단계의 목록과 추가가 다시 이용 가능해야 한다. 위계 변경으로 입력 상태를 소실시키지 않는다.
- wide: 목표 제안: 넓은 폭에서도 폼을 무제한 늘리지 않는다. 필요하면 현재 수단 요약을 옆에 보존하되 등록과 관리 행동을 구별하고 등록 중 다시 추가하는 충돌 행동은 사유와 함께 비활성화한다. 접근: 현재 단계·기존 수단 요약·입력의 읽기 순서를 구별한다. 등록 중 비활성인 관리 행동은 이유를 표시하고 취소/완료 후 실제 권한에 따라 복귀시킨다.
- 중간 폭: 폭보다 필드의 최소 읽기 공간과 키패드가 차지하는 높이를 함께 기준으로 배치한다. 두 필드 행이 라벨·오류를 수용하지 못하면 세로로 바꾸고, 낮은 높이에서는 현재 필드를 가시 영역으로 이동시키되 제목·복귀 접근을 보존한다.

적용 후 확인할 검사 **제안 — 미실행**:

- 카드 표시를 등록 또는 결제 성공으로 잘못 선언하지 않는가? → 목록 표시·등록 응답·인증·결제 상태를 별도 모델로 시험하고 권한 있는 응답 없는 완료 메시지가 없다.
- 좁은 오버레이와 실제 반응형 검증을 구별하는가? → 세 개의 독립된 목표 뷰포트와 중간 폭·낮은 높이를 실제 실행하고 단일 좁은 패널 스크린샷을 반응형 통과로 사용하지 않는다.
- 키패드가 열린 상태에서 전체 제목·현재 라벨·오류·취소를 읽고 조작할 수 있는가? → 최상단·중간 스크롤·확대·낮은 높이 테스트에서 제목을 확인하는 경로와 모든 입력 라벨 및 취소 접근이 유지된다.
- 가려진 값이 기록·미리보기·복귀 화면에 남지 않는가? → 비실제 테스트 값을 사용해 제공자 계약에 따른 가림·폐기·로그 제외를 별도 보안 검토하고 픽셀 가림만으로 보안 통과를 선언하지 않는다.
- 숫자 입력과 수정이 지원되는 입력 방식에서 완료 가능한가? → 승인된 키패드·일반 키보드·보조 기술의 지원 범위를 각각 실행해 한 단계 삭제·전체 지움·필드 이동·취소가 의도대로 작동한다.
- 등록 수단과 추가 경로를 혼동하지 않는가? → 빈 카드 범주와 여러 카드 범주에서 기존 항목은 식별·관리 역할, 추가 항목은 행동 역할로 명료하게 읽힌다.

제한: 좁은 웹 오버레이는 모바일 뷰포트나 리플로우의 증거가 아니다. 소스 반응형 동작은 전부 미확인이다. 등록 제목이 상단에서 잘려 있으므로 모든 제목·라벨·조작이 항상 보인다는 결론을 내릴 수 없다. 목록 카드 타일 일부도 가려져 있으며 등록 완료·결제 성공·카드 유효성·잔액 정확성을 검증하지 않았다. 값 가림·비순차 숫자 배열은 실제 보안·난수성·암호화·키패드 접근성 검증이 아니다. 계좌·카드·잔액·사용자 데이터와 입력값은 전사하지 않았으며 실거래나 외부 호출을 수행하지 않았다. 레시피는 관리→등록의 단계 분리를 제안한다. 이는 관찰된 동작이 아니며 프로젝트 적용 시 단계별 스펙·미저장 처리·복귀·서버 결과를 별도로 검증해야 한다.

익명화된 전체 8축 레시피·조작 5상태·스트레스 사례는 JSON의 `kurly-web-payment-registration` 항목에 있다.

### 13. 토스증권 웹 — 종목·뉴스·연관 결과를 분리한 검색 팔레트

과제: 하나의 질의로 성격이 다른 결과를 찾되 종목 이동·뉴스 읽기·연관 탐색을 혼동하지 않는다.

근거: [종목·뉴스 통합 검색 결과](https://uibowl.io/website/%ED%86%A0%EC%8A%A4%EC%A6%9D%EA%B6%8C?imgId=cm520gp9n0008ju0czmf3mxov).
정적 1프레임 범위이며 실행 또는 반응형 증거가 아니다.

구성 요소:

- **query**: 상단 둥근 입력 면에 질의가 보이며 검색 결과와 떨어져 있다.
- **category**: 검색 아래 분류 탭 중 하나가 진한 밑줄로 표시된다.
- **entity-results**: 넓은 왼쪽 영역에 이름·보조 식별자, 오른쪽 수치 열이 정렬되고 한 행의 배경이 회색이다.
- **article-results**: 왼쪽 아래는 별도 제목 아래 뉴스 제목·발행 시각·출처가 놓인다.
- **related-results**: 얇은 세로선 오른쪽에 연관 항목 제목·정보 아이콘과 항목 목록이 있다.
- **keyboard-hints**: 하단에 방향키·선택·ESC 지우기 키 안내가 작은 띠로 보인다. ESC를 닫기 기능으로 확인한 것은 아니다.

| 면 | 홈 화면을 어둡게 덮은 위에 흰 검색 패널과 회색 질의 입력, 회색 현재 행 면이 겹친다. |
| 경계·형태 | 패널의 둥근 외곽·입력 캡슐·탭 밑줄·결과 영역 분리선은 서로 다른 역할이다. |
| 깊이 | 덮개와 흰 패널이 검색을 앞세운다. 전체 뷰포트보다 주 콘텐츠 영역을 기준으로 놓인 모습이며 정확한 위치 규칙은 알 수 없다. |
| 타이포 | 종목명과 뉴스 제목은 보조 코드·시각·출처보다 강하다. 수치는 별도 우측 열이며 연관 제목도 독립적으로 보인다. |
| 간격·정렬 | 입력→탭→결과군→키 안내가 단계별로 떨어진다. 연관 열은 직접 결과 열보다 좁다. |
| 색의 역할 | 질의와 맞는 글자 일부는 파랑이고 수치에도 파랑/빨강이 있다. 일치 강조와 값 의미가 같은 색을 공유해 맥락 의존성이 있다. |
| 이미지 | 결과는 주로 텍스트와 작은 식별 표식으로 구별되며 큰 사진 카드가 검색을 지배하지 않는다. |
| 모션 | 정지 이미지로 모션의 실행·시간·이징·감소 설정을 확인할 수 없다. **미관찰** |

위계와 전이 가설:

- 먼저 읽히는 것: 현재 질의→결과 유형→직접 항목→읽을거리/연관 항목 순으로 결과 성격을 나눈다.
- 도우려는 판단: 찾던 대상으로 바로 이동할지, 관련 기사를 읽을지, 연관 대상으로 탐색을 넓힐지 결정한다.
- 가능한 제약: 동일한 질의 문자열이 직접 식별과 내용 탐색을 동시에 요구한다는 가설.
- 평탄화하면 잃는 것: 모두 같은 카드나 제목 목록으로 섞으면 결과 유형과 클릭 결과를 예측할 수 없고 관련 추천이 정확한 일치처럼 보인다.
- 대가: 분할 패널은 다양한 결과를 한눈에 보여주지만 좁은 폭에서 읽기/키보드 순서를 복잡하게 만들 수 있다.
- 맞지 않는 상황: 관련 근거 없는 추천으로 오른쪽 열을 채우거나 결과가 거의 없는 제품에 복잡한 2열 검색을 강제하면 해롭다.
- 필요한 데이터: 질의별 유형·중복 제거·현재 결과·검색 중/없음/실패·연관 근거·시각이 필요하다.
- 복제 금지 경계: 실제 금융 결과·회사 표식·브랜드 파랑을 복사하지 않고 결과 유형·읽기 관계만 추출한다.
- 적용 조건: 검색 결과에 유형·식별자·시각·출처가 실제로 구분된다. / 연관 결과는 직접 일치와 다른 데이터/설명 근거를 가진다.

정적 상태 근거:

- rest: 채워진 검색 결과가 있는 상태.
- selected: 한 결과 행의 회색 면과 키 안내가 보인다. 초점·마우스·키보드 중 무엇이 만든 상태인지는 확인되지 않는다.
- 미관찰: hover, focus-visible, disabled, loading, empty, error, success.

다른 제품에서의 크기별 재구성 **제안**:

- compact: 좁은 폭은 유형별 한 열 구획으로 재배치하고 직접 결과 이후 뉴스·연관 결과를 명시적으로 이어 놓는다. 접근: 질의 입력·유형 선택·결과·닫기 순으로 이동하며 결과 수와 갱신을 적절히 알린다.
- medium: 입력은 전체 폭, 직접/연관 결과는 충분한 이름 폭이 확보될 때만 분할한다. 접근: 오버레이라면 열림 초점·배경 접근·닫기/복귀를 실제 검증한다.
- wide: 직접 결과를 넓게 두고 연관 결과는 보조 열로 두되 탐색 순서가 시각 순서와 충돌하지 않게 한다. 접근: 키보드로 직접/뉴스/연관 결과에 모두 도달하고 현재 항목의 목적을 구별한다.
- 중간 폭: 목표 제안: 두 열 이름 공간이 부족해지기 전에 한 열 구획으로 전환하고 결과군과 초점 순서를 유지한다. 수치나 출처를 먼저 버리지 않는다.

적용 후 확인할 검사 **제안 — 미실행**:

- 다른 결과 유형을 구분해 실행하는가? → 직접 대상·뉴스·연관 결과의 라벨과 이동 결과가 실제로 일치한다.
- 하단 키 안내가 실제 동작인가? → 방향키·선택·질의 지우기의 실제 의미를 검증한다. 별도 닫기·복귀와 포인터/터치 접근도 검증하며 안내만으로 동작 성공을 주장하지 않는다.
- 늦은 응답이 새 질의를 덮는가? → 빠른 입력 전환과 취소 때 현재 질의에 속한 결과만 표시된다.
- 연관 결과가 정확한 일치처럼 보이는가? → 직접/연관을 구별하며 연관 근거가 없으면 빈 공간 채우기로 생성하지 않는다.

제한: 하단 키 안내는 실제 키보드 실행 증거가 아니다. 선택 행이 focus-visible이라는 근거는 없다. 실제 검색 정확도·지연·현재 사이트·모바일/다른 폭은 확인하지 않았다.

- 맞지 않는 상황: 단순 기사 리더나 가벼운 탐색 페이지에 거래 작업대의 열 수와 정보 밀도를 그대로 적용하면 해롭다.
- 필요한 데이터: 기준시각·단위·축·집계 기준·자료 지연·보유 상태·실행 권한과 서버 검증이 필요하다.
- 복제 금지 경계: 거래 버튼·신용/레버리지 선택의 존재를 안전성·법적 적합성 승인으로 보지 않으며 실제 투자 데이터나 브랜드를 복사하지 않는다.
- 적용 조건: 반복 비교할 구조화 데이터와 명확한 행/열 관계가 있다. / 고위험 행동은 실제 권한·검증·확인 단계와 연결된다.

정적 상태 근거:

- rest: 홈과 수치 상세가 채워진 상태.

다른 제품에서의 크기별 재구성 **제안**:

- compact: 한 열로 모듈을 재배치하되 대상·시각·조건·실행 확인을 숨기지 않는다. 반드시 동시 비교해야 하는 표만 지역 스크롤을 쓴다. 접근: 표의 행/열 머리와 지역 스크롤을 키보드로 접근하고 실행 전 조건에 도달하게 한다.
- medium: 차트와 값 비교를 우선하고 입력/기록은 명시된 구획으로 재배치하며 중요한 조건은 접어 숨기지 않는다. 접근: 차트 대체 정보·오류 설명·입력 단위를 읽을 수 있고 화면 전체 수평 스크롤을 피한다.
- wide: 차트·수치·입력·기록을 병치하되 논리적 탐색 순서와 최소 읽기 폭을 확보한다. 접근: 다열 시각 순서와 초점 순서를 대조하고 한 영역 갱신이 다른 입력을 초기화하지 않게 한다.
- 중간 폭: 목표 제안: 일정 열 수를 끝까지 유지하지 않는다. 비교 관계가 보존되는 구획으로 재배치하되 모든 숫자를 카드로 바꾸거나 중요한 실행 조건을 숨기지 않는다.

적용 후 확인할 검사 **제안 — 미실행**:

- 재배치하면 무엇을 비교하는지 사라지는가? → 좁은 폭·확대에서 행/열 머리·단위·현재 대상을 보존하고 값의 대응이 유지된다.
- 보기 좋은 버튼이 실제 권한보다 앞서는가? → 권한·검증·확인·중복 제출 처리가 검증되고 승인 없는 동작은 실행되지 않는다.
- 오래된 값이 실시간처럼 보이는가? → 기준시각과 지연/실패를 표시하며 갱신 때문에 사용자 입력이 손실되지 않는다.
- 모든 부분을 같은 카드/밀도로 만드는가? → 뉴스 읽기·수치 비교·조건 입력 각각의 읽기 순서와 목적별 공간을 검증한다.

제한: 과거 아카이브 정적 화면이며 현재 서비스 상태·실시간 동작·거래 안전성을 검증하지 않았다. 홈 하단 표는 머리 부분만 보여 전체 표 분석으로 계산하지 않았다. 수치 열 분석은 상세 화면에 근거한다. 정확한 CSS·폰트·색 토큰·모바일/중간 폭·접근성 적합성은 확인되지 않았다.

1. 서비스 기획의 사용자·과제·핵심 객체·정보 밀도·신뢰 위험·기기를 먼저 고정한다.
2. 위 이름이 아니라 **필요한 부분의 과제와 조건**으로 관련 분석을 찾는다. 맞지 않는 항목은 쓰지 않는다.

   이 연구의 국내 친숙성 기준이나 캡처 보유 자체는 프로젝트 Owner의 레퍼런스 선택을 대신하지 않는다.
4. 기존 KSR reference 흐름의 독립 검토·실제 Owner 선택을 거쳐 익명화된 레시피만 creator에 전달한다.
   이 전체 문서/JSON은 원 서비스 식별 정보를 포함하므로 creator 패킷으로 넘기지 않는다.
5. creator는 프로젝트 스타일에 맞는 실제 토큰·치수·폰트·선택자·상태·폭을
   [component specs](../component-recipes.md)에 작성한다. 관찰하지 않은 CSS 값을 출처 값처럼 적지 않는다.
6. 실제 후보를 브라우저로 검사하고 독립 critic이 보존 관계와 시각 품질을 비교한다.
   아래 검사 제안은 아직 실행/통과한 검사가 아니다. Owner 방향·색·정확한 산출물 승인은 별도다.

## 남은 커버리지와 정직한 완료 범위

이번 완료 단위는 **보관된 30개 프레임의 1차 정밀 정적 분석**이다.
열 개 제품 전체의 기능/디자인 시스템을 역설계하거나 직접 실사용한 결과가 아니다.
특히 다음은 열어 둔다.

- 같은 제품의 모바일·중간·데스크톱 대응 및 실제 클릭·키보드·모션·접근성.
- 실제 지도 조작, 소비자 커머스 목록/주문, 배달, 긴 출처 문서 읽기의 충분한 장면.
- 소비자 금융·네이버 계열 편중을 줄이는, 실제 과제에 맞는 추가 제품.
- 각 프로젝트의 선택·권리·원본 상태 최신성, 정확한 토큰/specs, 후보별 구현과 시각 검증.

현재 런타임 레지스트리, 설치본, 프로젝트 승인, 예전 receipt는 변경하지 않는다.
수집 수나 테스트 통과 수만으로 ‘사람이 만든 디자인’ 또는 좋은 결과를 보장하지 않는다.
이 자료는 모델 가중치를 학습시킨 것이 아니라 **재사용 가능한 외부 연구 근거**를 만든 것이다.
